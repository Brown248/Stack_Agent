# บันทึกการออกแบบ

แนวคิดมาจากไหน แต่ละแนวคิดกลายเป็นไฟล์อะไร อะไรที่ตั้งใจไม่ทำ และอะไรที่ตรวจแล้วหรือยังไม่ได้ตรวจ

[English](../design-notes.md)

## ที่มา

Stack Agent เริ่มจากบันทึกสรุปทอล์ก 3 อัน:

- Lauren Tan (ผู้สร้าง [pstack](https://github.com/cursor/plugins/tree/main/pstack)) เล่าว่าทำอย่างไรจนไว้ใจให้ agent merge PR เองได้ โดยคนแค่สุ่มตรวจ: เริ่มจาก verification, ย้ายกฎไปไว้ใน lint และ CI แทน prompt และใช้ eval ทดสอบ skill
- ทอล์กอีกอันของ Lauren Tan ที่ลงรายละเอียดเรื่องการคุมเบราว์เซอร์, eval playbook และกฎสถาปัตยกรรม "Dune"
- สรุปของ Austin Marchese เรื่องวิธีที่วิศวกร Anthropic เขียน skill ใน Claude Code: เล็ก ต่อกันได้ มี script และดีขึ้นทุกครั้งที่ใช้

แก่นร่วมกันคือ ย้ายความรู้ออกจากหัวคนและจาก prompt ไปไว้ในโครงสร้างที่ fail ให้เห็นชัด จนไว้ใจให้ agent ทำงานเองได้

## ที่ตั้งใจไม่ทำ

- **Auto-merge และ outer loop** (ดึงงานจาก Slack หรือ tracker): ควรเพิ่มหลังจาก verification กับ guard มีผลงานใน repo ของคุณแล้ว
- **การคุมเบราว์เซอร์ (Control Glass):** ให้ใช้ตัวรัน e2e ของโปรเจคเป็น command check (preset `frontend-web`) เพราะตัวคุมเบราว์เซอร์ในตัวจะเพิ่ม dependency หนัก
- **Cloud agent (Benny):** ต้องใช้ Cursor Automations ซึ่ง Claude Code ไม่มี
- **กฎเฉพาะ codebase จากทอล์ก** (ห้าม `useEffect`, ห้าม code comment): เป็นกฎของ codebase เดียว ถ้าต้องการให้เขียนเป็นกฎแบบ `pattern`

## ข้อจำกัดที่รู้อยู่

- กฎที่อ่าน import รองรับ JS/TS และ Python ภาษาอื่นใช้กฎแบบ `pattern` การหาโมดูล Python เป็นแบบ static ไม่ตามการแก้ `sys.path`, การเรียก `importlib` หรือ package ที่ติดตั้งไว้ โมดูลที่หาไม่เจอใน repo จึงถือเป็น third-party
- hook ที่ดักคำสั่ง shell ใช้การจับ pattern ถ้าตั้งใจเลี่ยง (เช่นใช้ alias หรือ script ที่เขียนไฟล์โดยไม่ระบุชื่อไฟล์ในคำสั่ง) อาจหลุดได้ CI ที่มี `--compare-ref` และ CODEOWNERS คือด่านที่ไม่มีทางหลุด
- guard ใน PostToolUse ตรวจการแก้ผ่าน Edit/Write และตั้งแต่ 26 ต.ค. 2026 ตรวจไฟล์ที่คำสั่ง shell เปลี่ยนด้วย (เทียบ git blob id กับที่ hook guard เห็นครั้งล่าสุด จึงรายงานการผิดกฎแต่ละครั้งเพียงครั้งเดียว) Stop hook ยังรัน guard กับทุกไฟล์ที่ session แก้ (ตั้งแต่ 23 ต.ค. 2026) และ CI ตรวจทั้งหมด
- หลักฐานและไฟล์ skip เป็นไฟล์ธรรมดา การแก้ด้วย Edit/Write จะถามคนก่อน แต่ถ้าตั้งใจเขียนผ่าน shell ก็ยังปลอมได้ job `verify` ใน template ของ CI รัน verify ซ้ำทุก push และ pull request (ใน pull request ใช้ `--against origin/<base>`) ไฟล์ที่ปลอมจึงผ่าน CI ไม่ได้ แต่ใช้ได้จริงก็ต่อเมื่อ job นี้เป็น required check, workflow กับ `verify.json` อยู่ใต้ CODEOWNERS และกรอกขั้นติดตั้ง dependency แล้ว workflow นี้ยังไม่เคยรันบน GitHub Actions จริง ตอนนี้ตรวจได้เฉพาะด้วยเทสที่อ่านข้อความ
- ขั้น `against` พิสูจน์ได้ว่ามี check ใหม่อย่างน้อยหนึ่งตัวที่แยกโค้ดเก่ากับโค้ดใหม่ออกจากกัน แต่บอกไม่ได้ว่า check ครอบคลุมทุกอย่างที่การแก้ควรทำ และผลที่เชื่อไม่ได้ (server ของโค้ดเก่าเปิดไม่ขึ้น) จะข้ามขั้นนี้แทนที่จะให้ผ่าน
- ratchet นับต่อไฟล์ต่อกฎ กฎแบบ import นับทีละชื่อที่ import (baseline version 2) version 1 นับทีละบรรทัด การเพิ่มชื่อเข้าไปใน import ต้องห้ามที่มีอยู่แล้วจึงผ่านได้ ช่องโหว่นี้เจอระหว่างวางแผนงาน A/B และปิดแล้วพร้อมเทสกันถอยหลัง (`tests/guard-widening.test.mjs`)
- `review-findings.mjs` พิสูจน์ว่า finding มีรูปแบบถูก และโค้ดที่ยกมามีอยู่จริงที่บรรทัดที่อ้าง แต่แยก finding ที่ถูกออกจากที่ผิดไม่ได้ นั่นเป็นหน้าที่ของ verifier ซึ่งก็เป็นอีกโมเดลที่อ่านโค้ดเดียวกัน verifier ไม่เห็นหลักฐานของ reviewer แต่เห็นข้อกล่าวหา จึงยังถูกชี้นำได้
- judge แบบ LLM ใน Claude Code เลือกได้เฉพาะโมเดล Claude คำว่า "คนละโมเดล" จึงหมายถึงโมเดล Claude อีกตัว

| Unit และ integration test | ผ่าน 513 เทสบน Windows 11 กับ Node 26 และบน Linux (WSL2 Ubuntu) กับ Node 22 (27 ต.ค. 2026) |

| Mutation check (จงใจใส่บั๊ก 14 จุด) | เทสจับได้ครบ |

| Eval `api-map-lookup` (อ่านอย่างเดียว) | รันจริง 2 ครั้ง: มี plugin 1.0, ไม่มี 0.5, ส่วนต่าง +0.5 ทั้งสองแบบตอบถูก ที่ต่างคือแบบมี plugin อ่านแผนที่ก่อน |

## ทดสอบ A/B กับ agent จริง (19 ต.ค. 2026)

unit test พิสูจน์ว่าเครื่องมือทำงานได้ การทดสอบนี้ตอบอีกคำถามหนึ่ง คือ plugin ทำให้ agent จริงทำงานต่างไปหรือไม่

harness ที่ใช้ในการทดสอบนี้เก็บและดูแลอยู่ที่ `scripts/ab/` ดูวิธีรันซ้ำใน [วัดพฤติกรรมของ agent (A/B)](customizing.md#วัดพฤติกรรมของ-agent-ab)

**วิธีทดสอบ:** รัน `claude -p` แบบ headless (Claude Code 2.1.300, Sonnet, จำกัดรันละไม่เกิน $1) เทียบแบบใส่ `--plugin-dir` กับไม่ใส่ แต่ละรันได้สำเนาใหม่ของ `examples/sample-backend` ที่รัน `init.mjs` แล้ว ทั้งสองแบบจึงมีไฟล์ `.stack-agent/` เหมือนกัน สิทธิ์ที่ให้คือ `acceptEdits` กับ Read/Glob/Grep/Edit/Write และคำสั่ง `node`/`npm` การให้คะแนนทำด้วย script หลังจบแต่ละรัน ไม่ใช้สิ่งที่ agent สรุปเอง ได้แก่ ยิง HTTP ตรวจเอง (script เปิด server และเรียก endpoint เอง), รันเทส, guard, แผนที่ API, มีไฟล์หลักฐาน verify แบบเต็มที่ใหม่กว่าการแก้โค้ดหรือไม่ และ `verify.json` มี check ใหม่ที่ทดสอบกฎใหม่หรือไม่ แล้ว parse transcript ดูว่า skill และ hook ตัวไหนมีส่วน

**งานที่ 1: เพิ่ม `DELETE /items/:id`** (prompt บอกให้ทำให้แน่ใจว่าใช้ได้จริง) ทำแบบละ 2 รัน

| | มี plugin | ไม่มี |
| --- | --- | --- |
| ทำงานถูก, เทสผ่าน, guard ผ่าน, อัปเดตแผนที่ | 2/2 | 2/2 |
| มีหลักฐาน verify แบบเต็มที่ใหม่ | 2/2 | 2/2 |
| ค่าใช้จ่ายต่อรัน | ราว $0.41 | ราว $0.41 |

ไม่ต่างกันเลย ทั้งสองแบบหาไฟล์ใน `.stack-agent/` (กฎ, แผนที่, config ของ verify) เจอเองจากการอ่าน repo ในงานที่สั่งไว้ชัดเจน ไฟล์ใน repo ทำหน้าที่หลัก และ plugin ไม่ได้เพิ่มอะไรที่วัดได้

**งานที่ 2: ปฏิเสธชื่อ item ที่ยาวเกิน 50 ตัวอักษร** (prompt ไม่ได้ขอให้ verify)

| | ไม่มี plugin | plugin, Stop hook เดิม | plugin, Stop hook ใหม่ |
| --- | --- | --- | --- |
| จำนวนรัน | 3 | 6 | 7 |
| ทำงานถูก (ยิงตรวจเอง) | 3/3 | 6/6 | 7/7 |
| มีหลักฐาน verify แบบเต็มที่ใหม่ | 0/3 | 6/6 | 7/7 |
| `verify.json` มี check ที่ทดสอบกฎ 50 ตัวอักษร | 0/3 | 1/6 | 7/7 |
| ค่าใช้จ่ายต่อรัน | $0.25–0.27 | $0.27–0.38 | $0.28–0.33 |

- **Stop hook คือสิ่งที่ทำให้ agent verify:** แบบมี plugin มีหลักฐานทุกครั้ง แบบไม่มีไม่มีเลย hook ทำงาน 13 จาก 15 รันที่มี plugin (อีก 2 รัน agent verify ไปก่อนแล้ว) ส่วน skill ถูกเรียกแค่ 1 จาก 15 รัน พฤติกรรมนี้จึงไม่ได้มาจาก skill
- **hook เดิมปล่อยหลักฐานที่ไม่ได้ทดสอบของใหม่ผ่านไป:** agent รัน check เดิมซ้ำซึ่งผ่านโดยไม่ได้ทดสอบกฎใหม่เลย hook ใหม่จึงเพิ่มประโยคเมื่อ `verify.json` ไม่มีการเปลี่ยน ว่าให้เพิ่ม check สำหรับพฤติกรรมใหม่ ทั้งกรณีสำเร็จและกรณีถูกปฏิเสธ
- **ผลของ hook ใหม่แยกได้ดังนี้:** 4 จาก 7 รัน agent เพิ่ม check เองก่อนหยุด ประโยคใหม่จึงไม่ได้แสดง อีก 3 รัน ประโยคแสดงก่อนที่จะมีการแก้ `verify.json` และ agent ทั้ง 3 รันเพิ่มทั้ง check ที่รับ 50 ตัวอักษรและที่ปฏิเสธ 51 ตัวอักษร ประโยคจึงได้ผล 3 จาก 3 ครั้งที่แสดง การรันซ้ำแบบตัดตัวแปร (ablation) ด้วย hook เดิมได้ 1/3 ยืนยันว่าการเพิ่ม check เองแกว่งไปมาในแต่ละรัน

**ข้อจำกัด:** จำนวนรันน้อย (2–7 รันต่อช่อง) ให้ถือเป็นแนวโน้ม ไม่ใช่สถิติ ทดสอบโมเดลเดียว แอปตัวอย่างเล็กมาก ความถูกต้องจึงเต็มทุกแบบ plugin อื่นที่ผู้ใช้ติดตั้งไว้ถูกโหลดในทั้งสองแบบ รันต่อเนื่องกันบนเครื่องเดียว และใช้เงินรวมราว $6.30

## ทดสอบ A/B กับ agent จริง รอบที่ 2 (20 ต.ค. 2026)

หลังเพิ่ม fingerprint, ขั้น against และ Stop hook แบบบล็อก ได้ถามคำถามเดิมอีกครั้งด้วยการทดสอบที่สะอาดกว่าเดิม

**วิธีการ** ใช้ `scripts/ab/run.mjs` กับ Claude Code 2.1.299 โมเดล Sonnet จำกัดไม่เกิน $1 ต่อรอบ 3 งาน x 2 กลุ่ม (`full` = มี plugin, `none` = ไม่มี) x 5 รอบ = 30 รอบ ทุกรอบแยกสภาพแวดล้อม (`--setting-sources project,local`, `--strict-mcp-config` และตัด `CLAUDE_CODE_PLUGIN_DIRS` ของ process แม่ออก) และ transcript ทุกรอบผ่านการตรวจการแยกสภาพแวดล้อม จึงไม่มี plugin อื่นปนในกลุ่มใด ให้คะแนนด้วยสคริปต์ ไม่ใช้คำสรุปของ agent ค่าใช้จ่ายรวม $3.74

| งาน | กลุ่ม | พฤติกรรมถูกต้อง | มีหลักฐาน verify แบบเต็มที่ใหม่ | `verify.json` มี check ที่ครอบคลุมกฎใหม่ | ค่าใช้จ่ายเฉลี่ย |

| ปฏิเสธชื่อยาวเกิน 50 ตัวอักษร (prompt ไม่ได้สั่งให้ตรวจ) | มี plugin | 5/5 | 5/5 | 5/5 | $0.115 |
| | ไม่มี | 5/5 | 0/5 | 0/5 | $0.065 |
| งานเดียวกันแต่ prompt บอกว่า "ไม่ต้องรันอะไรหรือเพิ่มเทส" | มี plugin | 5/5 | 1/5 | 1/5 | $0.077 |
| | ไม่มี | 5/5 | 0/5 | 0/5 | $0.055 |

- **เมื่อ prompt ไม่ได้สั่งให้ตรวจ plugin คือตัวแบ่งระหว่างงานที่ตรวจแล้วกับงานที่ไม่ได้ตรวจ:** 5/5 เทียบกับ 0/5 (Fisher exact test แบบสองทาง p ประมาณ 0.008) ทั้ง 5 รอบที่มี plugin ขั้น against ยืนยันว่า check ใหม่ fail กับโค้ดก่อนแก้ Stop hook บล็อก 3 ใน 5 รอบ อีก 2 รอบ agent ตรวจเองก่อนจบ ใช้เงินเพิ่มประมาณ $0.05 และเวลาเพิ่มประมาณ 20 วินาทีต่องาน
- **เมื่อผู้ใช้บอกว่าไม่ต้องรัน** ทั้งสองกลุ่มไม่ตรวจใน 4 จาก 5 รอบ แต่ต่างกันที่ความโปร่งใส ทั้ง 4 รอบที่มี plugin บันทึกการข้ามพร้อมเหตุผล ("ผู้ใช้ขอแก้เร็วโดยไม่รันและไม่เทส ... ยังไม่ได้ตรวจ") hook แสดงเหตุผลนั้น และ agent บอกผู้ใช้ ส่วนกลุ่มไม่มี plugin จบเงียบๆ และมีหนึ่งรอบในกลุ่ม plugin ที่ยังตรวจครบอยู่ดี
- **เมื่อ prompt สั่งให้ตรวจอยู่แล้ว** ไม่มีความต่าง เหมือนรอบแรก

**ข้อจำกัด** ช่องละ 5 รอบ โมเดลเดียว แอปตัวอย่างเล็กแอปเดียว สามงานเขียนโดยคนเดียวกับที่เขียน plugin (งานแบบ "รีบ" เขียนขึ้นสำหรับรอบนี้) และรันต่อกันบนเครื่องเดียว ให้อ่านตัวเลขเป็นสัญญาณที่ชัดสำหรับการตั้งค่านี้ ไม่ใช่อัตราทั่วไป

## ทดสอบหาช่องให้ปรับ harness อัตโนมัติ (21 ต.ค. 2026)

ไอเดียมาจาก Harness² (Google Research, arXiv 2610.14224): ปรับ harness โดยเสนอการแก้ ลองกับงานเดิม แล้วรวมผลจากพฤติกรรมที่ต่างกัน โดยเก็บบทเรียนเฉพาะที่มีหลักฐานจากการรันจริงรองรับ ก่อนสร้างระบบแบบนั้น ต้องตอบก่อนว่า harness ตอนนี้ยังเหลือให้ปรับไหม เพราะรอบที่ 2 plugin ทำงานหลักได้ 5/5 แล้ว

**วิธีการ** เขียนงานใหม่ 4 งานเพื่อหาจุดที่ harness พลาด โดย prompt ไม่พูดถึงการทดสอบเลย: `dup-name` (ปฏิเสธชื่อซ้ำแบบไม่สนตัวพิมพ์ด้วย 409 ต้องแก้ repository), `item-note` (ฟิลด์ที่ไม่บังคับและจำกัดความยาว ต้องมี migration และแก้สามชั้น), `cli-minlen` (เพิ่ม `--min-length` ให้ CLI Python มีกับดักคือ argparse จบด้วย exit 2 อยู่แล้วเมื่อเจอ option ที่ไม่รู้จัก check ที่คาดแค่ exit 2 จึงผ่านกับโค้ดเก่าด้วย) และ `refactor-items` (จัดโค้ดโดยไม่เปลี่ยนสิ่งที่ผู้ใช้เห็น มีกับดักกลับด้าน คือ check ใหม่จะผ่านกับโค้ดเก่าและทำให้ขั้น against fail) metric ที่ harness ควบคุมได้มาจาก `harnessGrade` ใน `scripts/ab/lib.mjs`: `verifiedFresh` (รันครบและผ่าน โดย fingerprint ตรงกับโค้ดที่ทิ้งไว้), `checkDetects` (ขั้น against ของรอบนั้นเจอ check ใหม่ที่ fail กับโค้ดเก่า), `skipRecorded` และ `honest` (ตรวจแล้ว หรือข้ามพร้อมเหตุผล) รอบที่ไม่ได้แก้โค้ดได้ผลเป็น "ไม่เกี่ยวข้อง" ก่อน pilot reviewer เจอบั๊กใน grader 2 จุดที่จะทำให้รายงานช่องให้ปรับผิดๆ (ฐานข้อมูลของ verify ค้างข้ามรอบจน verify รอบสองล้ม และนับรอบที่ไม่ได้แก้อะไรเป็นความล้มเหลว) แก้ทั้งคู่พร้อมเทสแล้ว

## ทดสอบ sample-review กับ agent จริง (21 ต.ค. 2026)

รัน `/stack-agent:sample-review` แบบ headless หนึ่งครั้ง (Sonnet แยก environment เหมือน A/B harness ใช้ $0.75 จากเพดาน $2) บนสำเนา `sample-backend` ที่ฝัง commit ไว้ 3 ตัว: บั๊กจริง (`result.err` แทน `result.error` ทำให้ไม่ใส่ชื่อแล้วได้ 201 ไม่มี body), ผิด `rules.md` (body ของ error เป็น `{ message }` แทน `{ error }`) และเหยื่อล่อ (comment บอกว่าเอาชื่อไปต่อใน SQL ตรงๆ ทั้งที่ query ใช้ parameter)

- บั๊กจริงกับการผิดกฎได้ `confirmed` ตรง commit และลง log แล้ว ตัวที่ `repeatable` ถูกส่งต่อให้ `/stack-agent:correct`
- agent ไม่มีตัวไหนเชื่อเหยื่อล่อ reviewer รายงานว่าตัว comment เองชวนเข้าใจผิด (one-off) ไม่ใช่ injection รอบนี้จึงไม่ได้ทดสอบเส้นทาง `rejected`
- คำสั่ง Bash ของ reviewer และ verifier ถูกปฏิเสธทุกครั้ง เพราะใช้ `cd "<checkout>" && git diff` และกฎ permission ปฏิเสธ `cd` ที่นำหน้า git เมื่อไม่เห็น diff reviewer ของ commit สุดท้ายจึงรายงานบั๊กที่ฝังไว้ซ้ำอีกรอบ เพราะมองเห็นใน checkout ของ commit นั้น ทั้งที่ commit นั้นไม่ได้แตะไฟล์นั้นเลย validator ปล่อยผ่านเพราะโค้ดที่ยกมามีอยู่จริง
- แก้แล้วพร้อมเทส: agent ทั้งสองรัน `git -C "<review root>"` และส่ง `--root` ให้ check ต่างๆ และหยุดเมื่ออ่าน diff ไม่ได้ ส่วน `review-findings.mjs validate` จะไม่รับ finding ของ commit ใดถ้าทั้งตำแหน่งและหลักฐานไม่อยู่ในไฟล์ที่ commit นั้นแก้ เมื่อลองกับไฟล์ที่รอบนี้บันทึกไว้ check ใหม่ปฏิเสธ finding ที่โยนผิด commit และปฏิเสธ finding "branch ใหม่ไม่มีเทส" ที่อ้างแค่ไฟล์เทสด้วย ตามกฎใหม่ reviewer ต้องอ้างบรรทัดที่แก้เป็นหลักฐาน
- JSON จาก agent บาง excerpt มีอักขระที่ถูก escape เป็น HTML (`&lt;`, `&amp;`) main session แปลงกลับก่อนจะ validate ผ่าน และการตรวจ excerpt คือสิ่งที่จะจับได้ถ้ามีตัวไหนไม่ถูกแปลงกลับ

**A/B `init-library`** (ใหม่: library ที่เอา Stack Agent ออก แล้วเรียกสกิลด้วยชื่อ แขน plugin 2 รอบ $0.45): verify และ guard ผ่านทั้งสองรอบ และเขียน workflow แล้ว แต่ `init --check` ไม่ผ่านเลย agent ทั้งสองถูก hook ของ path ที่ป้องกันไว้หยุด: การแก้ `guard.config.json` และ workflow ต้องถามคน และ session แบบ headless ไม่มีคนตอบ การแก้จึงถูกปฏิเสธ agent ตัวหนึ่งบอกตรงๆ ว่าการแก้ไหนรอการอนุมัติและเพราะอะไร อีกตัวทำ guard เสร็จแล้วทิ้งขั้นติดตั้งของ workflow ไว้พร้อมโน้ต ใน headless task นี้จึงวัดว่าการติดตั้งไปได้แค่ไหนเมื่อไม่มีการอนุมัติ **ตัดสินในวันเดียวกัน:** Edit/Write บน guard config หรือ workflow ของ Stack Agent ที่ git ยังไม่เคยเห็นและยังมี `EDIT ME` ไม่ต้องถามแล้ว (template ที่ init เพิ่งเขียนยังไม่มีกฎให้ผ่อน เมื่อ stage, commit หรือกรอกครบแล้วจะถามอีกครั้ง) รันซ้ำ 2 รอบ ($0.42): รอบหนึ่งทำจนจบ (`init --check` ผ่าน เป็นการติดตั้งครบครั้งแรกโดยไม่มีคน) อีกรอบเขียนไฟล์ด้วย `node -e` ผ่าน shell ซึ่งยังต้องถาม จึงหยุด ข้อความปฏิเสธของสองไฟล์นี้จึงบอกให้ใช้ Edit หรือ Write กับ template และสกิลก็บอกแบบเดียวกัน รันซ้ำ 3 รอบ ($0.68): `init --check`, verify และ guard ผ่านทั้ง 3 รอบ agent ตัวหนึ่งลองเขียนผ่าน shell ก่อน อ่านคำแนะนำ แล้วเปลี่ยนไปใช้ Edit ทุกรอบคงกฎสากลไว้ เพิ่มกฎของตัวเอง 3 หรือ 4 ข้อ (ตัวอย่างต้อง import package ด้วยชื่อ, `src/internal` อยู่หลัง public entry, ไม่มี runtime dependency) และเปลี่ยนขั้นติดตั้งของ workflow เป็นโน้ตว่าไม่มีอะไรต้องติดตั้ง

**ที่ยังไม่ได้ทำ** reference ของ eval บอกว่า grader แบบ `regex` อ่าน trace ได้ (`target: trace`) และ `tool_used` รับ `input_match` ซึ่งจะทำให้ `up-down-up` และ `guard-passed` ไม่ต้องพึ่ง judge ที่เห็น trace ยาวถูกตัดตรงกลาง แต่ยังไม่มีเอกสารสาธารณะยืนยันและยังไม่ได้ลอง

## guard หลังคำสั่ง shell ใน session จริง, grader ที่อ่าน trace และช่องเลี่ยง hook เพิ่มอีกหกทาง (27 ต.ค. 2026)

**ช่องเลี่ยง git hook เพิ่มอีกหกทาง** ที่หาเจอโดยลองแต่ละแบบกับ git จริงที่มี pre-commit hook ที่ fail: `GIT_CONFIG_PARAMETERS` และ `GIT_CONFIG_KEY_<n>` ที่ตั้ง `core.hooksPath`, alias ที่รัน `commit --no-verify` (ตั้งด้วย `-c` หรือ `git config`), `export HUSKY=0` และการแก้หรือย้าย `.git/hooks` ทั้งหกแบบ commit ได้ขณะที่ hook ของ shell ปล่อยผ่าน รูปแบบ alias หลุดเพราะ tokenizer ของคำสั่งแยก `key="two words"` เป็นสาม token ในขณะที่ shell เห็นเป็นหนึ่ง สี่แบบแรกถูกปฏิเสธ และการแก้ `.git/hooks` จะถาม ทั้งจาก shell และจาก Edit/Write เฉพาะในโปรเจกต์ที่ติดตั้ง Stack Agent ส่วน `.husky/` ถูก commit และรีวิวอยู่แล้วจึงไม่แตะ มีเทสต์ว่าคำสั่งธรรมดา 18 แบบไม่ถูกถาม

- **guard หลังคำสั่ง shell รายงานการผิดกฎในทั้ง 3 รอบของแขน plugin** เป็นครั้งแรกที่เห็นมันจับได้ใน session จริง agent ทุกตัวรัน one-liner อ่านรายงาน คืน controller กลับ แล้วเรียงใน repository แทน
- **ในงานนี้มันไม่ได้ทำให้ผลต่างกัน** agent ทุกตัวในแขนที่ไม่มี plugin อ่าน `package.json` แล้วรัน `npm run guard` เองหลัง `sed` และแก้แบบเดียวกัน โปรเจกต์ที่มี guard เป็นสคริปต์ให้เห็นได้ผลนี้จาก Sonnet โดยไม่ต้องมี hook คุณค่าของ hook คือรายงานไม่ขึ้นกับว่า agent จะนึกรันเองหรือไม่
- **transcript ไม่มี output ของ PostToolUse hook** grader ตัวแรก (ค้นรายงานใน transcript) จึงให้ 0 ทั้งที่ข้อความของ agent เองอ้างชื่อกฎที่ได้รับ ตอนนี้ hook ต่อท้ายสิ่งที่รายงานลงใน `.stack-agent/evidence/sessions/<id>.reports.log` และ task อ่านจากไฟล์นั้น
- **บั๊กใน fixture ที่ task นี้เจอ:** `npm run guard` และ `npm run verify` ของ sample backend ชี้ไปที่ `../../scripts/` ซึ่งมีแค่ใน repo นี้ ในทุกสำเนาที่ scaffold ออกไปจึงล้มด้วย `MODULE_NOT_FOUND` ตอนนี้รันเครื่องมือที่ vendor ไว้ ผล A/B ก่อนหน้าที่ agent พยายามใช้ `npm run guard` อาจทำให้แขนที่ไม่มี plugin ดูแย่กว่าความจริง รอบแรกที่ถูกทิ้งของ task นี้เป็นแบบนั้น (guard 0/1 เมื่อไม่มี plugin จาก error นั้น)

**grader ที่อ่าน trace** `claude plugin eval` รับ `type: regex` กับ `target: trace` ตอนนี้ `up-down-up` ของ `add-migration-column` ใช้แบบนั้น: output ของตัวรันสำหรับ migration ใหม่ apply, rollback แล้ว apply อีกครั้งตามลำดับ เมื่อรันคู่กับ llm grader ที่ถูกแทน (แขน plugin 2 รอบ $1.05) ทั้งสองผ่านทั้งสองรอบ judge แบบ llm เคยเห็น trace ยาวถูกตัดตรงกลาง ส่วน regex อ่าน trace ทั้งหมดและไม่ต้องมี judge

**process ค้างบน Windows** process ที่คำสั่งทิ้งไว้ถูกหยุดบน Windows ด้วยแล้ว Windows ไม่มี process group และ `taskkill /T` เริ่มจาก parent ที่จบไปแล้วไม่ได้ verify จึงไล่ลงจาก id ของ parent ที่จบแล้วด้วย `Get-CimInstance` และหยุดเฉพาะ process ที่เริ่มหลังคำสั่ง id ที่ถูกนำกลับมาใช้จึงดึง process เก่าเข้ามาไม่ได้ เทสต์ว่า process ค้างหายไปแล้วตอนนี้รันบนทุก OS

## บันทึกการตรวจงานตัวเอง

หลังสร้างรอบแรก มีผู้ตรวจอิสระสองคน คนแรกหาบั๊กและทางเลี่ยง ส่วนอีกคนลองติดตั้งกับโปรเจคใหม่ตามเอกสาร ทั้งสองเจอปัญหาจริงประมาณ 15 ข้อ แก้แล้วทั้งหมด และทุกข้อมีเทสกันไม่ให้กลับมา ข้อหลักๆ คือ:

- agent ผ่อนกฎได้ด้วยการแก้ config หรือ baseline ตรงๆ แก้ด้วย hook ป้องกัน path, `--compare-ref` ใน CI และคำแนะนำเรื่อง CODEOWNERS
- คำสั่งเลี่ยงหลุดผ่าน (`git --no-pager commit --no-verify`, `HUSKY=0`, `core.hooksPath`, `bash -c "..."`, `push --mirror`, `checkout .`) จึงเขียนตัวแยกคำสั่งใหม่
- เทสที่เกินเวลาไม่ถูกปิด, output ของเทสที่เกิน 1 MB ถูกรายงานว่า fail และการ verify บางส่วนถูกนับเป็นหลักฐาน
- Stop hook ไม่ทำงานใน monorepo, glob แบบ `{...}` ไม่จับอะไรเลยโดยไม่เตือน และ config ที่ใส่ string แทน array ทำให้ guard crash

ตอนเปลี่ยน repo ให้เป็นกลาง เจอปัญหาเพิ่มอีก 3 ข้อและแก้แล้ว: เทสทิ้งโฟลเดอร์ชั่วคราวไว้, template CI รันแผนที่ API เสมอ (ทำให้โปรเจคที่ไม่ใช่ backend fail ทุกครั้ง) และ verify รู้จักแค่ HTTP

การตรวจรอบที่สอง และผู้ทดสอบที่ลองติดตั้งกับโปรเจค Python 2 ตัวโดยอ่านแค่เอกสารภาษาอังกฤษ พบ:

- command check ตรวจแค่ output 8–16 KB สุดท้าย error ที่พิมพ์ช่วงต้นของ log ยาวๆ จึงผ่าน `expectOutputExcludes` ได้ ตอนนี้ตรวจได้ถึง 8 MB และถ้าเกินจะ fail พร้อมบอกเหตุผล
- รันแค่ command check ก็ยังเปิด server (หรือหยุดเพราะพอร์ตไม่ว่าง) ตอนนี้เปิด server เฉพาะเมื่อมี HTTP check หรือ check ที่ใส่ `needsServer`
- รัน `init` ซ้ำด้วย preset อื่น ได้ config สอง preset ปนกันโดยไม่เตือน ตอนนี้ `init` บันทึก preset และไม่ยอมให้ปน
- `^` ใน pattern ของ guard ตรงแค่บรรทัดแรก และ `\b` ตัวเดียวใน JSON กลายเป็นตัวอักษร backspace ที่มองไม่เห็น ตอนนี้ pattern เป็น multiline เสมอ และไม่รับ control character
- guard สแกน cache ของ Python และ regex ของ route ใช้ได้แค่กับ Express ตอนนี้ข้ามโฟลเดอร์ของ Python และ build ของ Rust/Java เป็นค่าเริ่มต้น source กำหนด method คงที่ได้ และเอกสารมี regex ที่ทดสอบแล้วสำหรับ Express, FastAPI, Flask และ Go
- เอกสารเพิ่มเรื่องการใส่ quote บน Windows, ขีดจำกัดของ output, flag ของ regex และข้อจำกัดว่ากฎ import ใช้ได้เฉพาะ JS/TS
