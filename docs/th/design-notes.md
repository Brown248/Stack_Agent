# บันทึกการออกแบบ

แนวคิดมาจากไหน แต่ละแนวคิดกลายเป็นไฟล์อะไร อะไรที่ตั้งใจไม่ทำ และอะไรที่ตรวจแล้วหรือยังไม่ได้ตรวจ

[English](../design-notes.md)

## ที่มา

Stack Agent เริ่มจากบันทึกสรุปทอล์ก 3 อัน:

- Lauren Tan (ผู้สร้าง [pstack](https://github.com/cursor/plugins/tree/main/pstack)) เล่าว่าทำอย่างไรจนไว้ใจให้ agent merge PR เองได้ โดยคนแค่สุ่มตรวจ: เริ่มจาก verification, ย้ายกฎไปไว้ใน lint และ CI แทน prompt และใช้ eval ทดสอบ skill
- ทอล์กอีกอันของ Lauren Tan ที่ลงรายละเอียดเรื่องการคุมเบราว์เซอร์, eval playbook และกฎสถาปัตยกรรม "Dune"
- สรุปของ Austin Marchese เรื่องวิธีที่วิศวกร Anthropic เขียน skill ใน Claude Code: เล็ก ต่อกันได้ มี script และดีขึ้นทุกครั้งที่ใช้

แก่นร่วมกันคือ ย้ายความรู้ออกจากหัวคนและจาก prompt ไปไว้ในโครงสร้างที่ fail ให้เห็นชัด จนไว้ใจให้ agent ทำงานเองได้

## ที่ตั้งใจไม่ทำ

- **Auto-merge และ outer loop** (ดึงงานจาก Slack หรือ tracker): ควรเพิ่มหลังจาก verification กับ guard มีผลงานใน repo ของคุณแล้ว
- **การคุมเบราว์เซอร์ (Control Glass):** ให้ใช้ตัวรัน e2e ของโปรเจคเป็น command check (preset `frontend-web`) เพราะตัวคุมเบราว์เซอร์ในตัวจะเพิ่ม dependency หนัก
- **Cloud agent (Benny):** ต้องใช้ Cursor Automations ซึ่ง Claude Code ไม่มี
- **กฎเฉพาะ codebase จากทอล์ก** (ห้าม `useEffect`, ห้าม code comment): เป็นกฎของ codebase เดียว ถ้าต้องการให้เขียนเป็นกฎแบบ `pattern`

## ข้อจำกัดที่รู้อยู่

- กฎที่อ่าน import รองรับ JS/TS และ Python ภาษาอื่นใช้กฎแบบ `pattern` การหาโมดูล Python เป็นแบบ static ไม่ตามการแก้ `sys.path`, การเรียก `importlib` หรือ package ที่ติดตั้งไว้ โมดูลที่หาไม่เจอใน repo จึงถือเป็น third-party
- hook ที่ดักคำสั่ง shell ใช้การจับ pattern ถ้าตั้งใจเลี่ยง (เช่นใช้ alias หรือ script ที่เขียนไฟล์โดยไม่ระบุชื่อไฟล์ในคำสั่ง) อาจหลุดได้ CI ที่มี `--compare-ref` และ CODEOWNERS คือด่านที่ไม่มีทางหลุด
- guard ใน PostToolUse ตรวจการแก้ผ่าน Edit/Write และตั้งแต่ 26 ต.ค. 2026 ตรวจไฟล์ที่คำสั่ง shell เปลี่ยนด้วย (เทียบ git blob id กับที่ hook guard เห็นครั้งล่าสุด จึงรายงานการผิดกฎแต่ละครั้งเพียงครั้งเดียว) Stop hook ยังรัน guard กับทุกไฟล์ที่ session แก้ (ตั้งแต่ 23 ต.ค. 2026) และ CI ตรวจทั้งหมด
- หลักฐานและไฟล์ skip เป็นไฟล์ธรรมดา การแก้ด้วย Edit/Write จะถามคนก่อน แต่ถ้าตั้งใจเขียนผ่าน shell ก็ยังปลอมได้ job `verify` ใน template ของ CI รัน verify ซ้ำทุก push และ pull request (ใน pull request ใช้ `--against origin/<base>`) ไฟล์ที่ปลอมจึงผ่าน CI ไม่ได้ แต่ใช้ได้จริงก็ต่อเมื่อ job นี้เป็น required check, workflow กับ `verify.json` อยู่ใต้ CODEOWNERS และกรอกขั้นติดตั้ง dependency แล้ว workflow นี้รันบน GitHub Actions จริงครั้งแรกเมื่อ 27 ต.ค. 2026 (ดู "เทมเพลต CI ของผู้ใช้บน GitHub Actions จริง" ด้านล่าง) ก่อนหน้านั้นตรวจได้เฉพาะด้วยเทสที่อ่านข้อความ
- ขั้น `against` พิสูจน์ได้ว่ามี check ใหม่อย่างน้อยหนึ่งตัวที่แยกโค้ดเก่ากับโค้ดใหม่ออกจากกัน แต่บอกไม่ได้ว่า check ครอบคลุมทุกอย่างที่การแก้ควรทำ และผลที่เชื่อไม่ได้ (server ของโค้ดเก่าเปิดไม่ขึ้น) จะข้ามขั้นนี้แทนที่จะให้ผ่าน
- ratchet นับต่อไฟล์ต่อกฎ กฎแบบ import นับทีละชื่อที่ import (baseline version 2) version 1 นับทีละบรรทัด การเพิ่มชื่อเข้าไปใน import ต้องห้ามที่มีอยู่แล้วจึงผ่านได้ ช่องโหว่นี้เจอระหว่างวางแผนงาน A/B และปิดแล้วพร้อมเทสกันถอยหลัง (`tests/guard-widening.test.mjs`)
- `review-findings.mjs` พิสูจน์ว่า finding มีรูปแบบถูก และโค้ดที่ยกมามีอยู่จริงที่บรรทัดที่อ้าง แต่แยก finding ที่ถูกออกจากที่ผิดไม่ได้ นั่นเป็นหน้าที่ของ verifier ซึ่งก็เป็นอีกโมเดลที่อ่านโค้ดเดียวกัน verifier ไม่เห็นหลักฐานของ reviewer แต่เห็นข้อกล่าวหา จึงยังถูกชี้นำได้
- judge แบบ LLM ใน Claude Code เลือกได้เฉพาะโมเดล Claude คำว่า "คนละโมเดล" จึงหมายถึงโมเดล Claude อีกตัว

| Mutation check (จงใจใส่บั๊ก 14 จุด) | เทสจับได้ครบ |

| Eval `api-map-lookup` (อ่านอย่างเดียว) | รันจริง 2 ครั้ง: มี plugin 1.0, ไม่มี 0.5, ส่วนต่าง +0.5 ทั้งสองแบบตอบถูก ที่ต่างคือแบบมี plugin อ่านแผนที่ก่อน |

## ทดสอบ A/B กับ agent จริง (19 ต.ค. 2026)

unit test พิสูจน์ว่าเครื่องมือทำงานได้ การทดสอบนี้ตอบอีกคำถามหนึ่ง คือ plugin ทำให้ agent จริงทำงานต่างไปหรือไม่

harness ที่ใช้ในการทดสอบนี้เก็บและดูแลอยู่ที่ `scripts/ab/` ดูวิธีรันซ้ำใน [วัดพฤติกรรมของ agent (A/B)](customizing.md#วัดพฤติกรรมของ-agent-ab)

**วิธีทดสอบ:** รัน `claude -p` แบบ headless (Claude Code 2.1.300, Sonnet, จำกัดรันละไม่เกิน $1) เทียบแบบใส่ `--plugin-dir` กับไม่ใส่ แต่ละรันได้สำเนาใหม่ของ `examples/sample-backend` ที่รัน `init.mjs` แล้ว ทั้งสองแบบจึงมีไฟล์ `.stack-agent/` เหมือนกัน สิทธิ์ที่ให้คือ `acceptEdits` กับ Read/Glob/Grep/Edit/Write และคำสั่ง `node`/`npm` การให้คะแนนทำด้วย script หลังจบแต่ละรัน ไม่ใช้สิ่งที่ agent สรุปเอง ได้แก่ ยิง HTTP ตรวจเอง (script เปิด server และเรียก endpoint เอง), รันเทส, guard, แผนที่ API, มีไฟล์หลักฐาน verify แบบเต็มที่ใหม่กว่าการแก้โค้ดหรือไม่ และ `verify.json` มี check ใหม่ที่ทดสอบกฎใหม่หรือไม่ แล้ว parse transcript ดูว่า skill และ hook ตัวไหนมีส่วน

**งานที่ 1: เพิ่ม `DELETE /items/:id`** (prompt บอกให้ทำให้แน่ใจว่าใช้ได้จริง) ทำแบบละ 2 รัน

| | มี plugin | ไม่มี |
| --- | --- | --- |
| ทำงานถูก, เทสผ่าน, guard ผ่าน, อัปเดตแผนที่ | 2/2 | 2/2 |
| มีหลักฐาน verify แบบเต็มที่ใหม่ | 2/2 | 2/2 |
| ค่าใช้จ่ายต่อรัน | ราว $0.41 | ราว $0.41 |

ไม่ต่างกันเลย ทั้งสองแบบหาไฟล์ใน `.stack-agent/` (กฎ, แผนที่, config ของ verify) เจอเองจากการอ่าน repo ในงานที่สั่งไว้ชัดเจน ไฟล์ใน repo ทำหน้าที่หลัก และ plugin ไม่ได้เพิ่มอะไรที่วัดได้

**งานที่ 2: ปฏิเสธชื่อ item ที่ยาวเกิน 50 ตัวอักษร** (prompt ไม่ได้ขอให้ verify)

| | ไม่มี plugin | plugin, Stop hook เดิม | plugin, Stop hook ใหม่ |
| --- | --- | --- | --- |
| จำนวนรัน | 3 | 6 | 7 |
| ทำงานถูก (ยิงตรวจเอง) | 3/3 | 6/6 | 7/7 |
| มีหลักฐาน verify แบบเต็มที่ใหม่ | 0/3 | 6/6 | 7/7 |
| `verify.json` มี check ที่ทดสอบกฎ 50 ตัวอักษร | 0/3 | 1/6 | 7/7 |
| ค่าใช้จ่ายต่อรัน | $0.25–0.27 | $0.27–0.38 | $0.28–0.33 |

- **Stop hook คือสิ่งที่ทำให้ agent verify:** แบบมี plugin มีหลักฐานทุกครั้ง แบบไม่มีไม่มีเลย hook ทำงาน 13 จาก 15 รันที่มี plugin (อีก 2 รัน agent verify ไปก่อนแล้ว) ส่วน skill ถูกเรียกแค่ 1 จาก 15 รัน พฤติกรรมนี้จึงไม่ได้มาจาก skill
- **hook เดิมปล่อยหลักฐานที่ไม่ได้ทดสอบของใหม่ผ่านไป:** agent รัน check เดิมซ้ำซึ่งผ่านโดยไม่ได้ทดสอบกฎใหม่เลย hook ใหม่จึงเพิ่มประโยคเมื่อ `verify.json` ไม่มีการเปลี่ยน ว่าให้เพิ่ม check สำหรับพฤติกรรมใหม่ ทั้งกรณีสำเร็จและกรณีถูกปฏิเสธ
- **ผลของ hook ใหม่แยกได้ดังนี้:** 4 จาก 7 รัน agent เพิ่ม check เองก่อนหยุด ประโยคใหม่จึงไม่ได้แสดง อีก 3 รัน ประโยคแสดงก่อนที่จะมีการแก้ `verify.json` และ agent ทั้ง 3 รันเพิ่มทั้ง check ที่รับ 50 ตัวอักษรและที่ปฏิเสธ 51 ตัวอักษร ประโยคจึงได้ผล 3 จาก 3 ครั้งที่แสดง การรันซ้ำแบบตัดตัวแปร (ablation) ด้วย hook เดิมได้ 1/3 ยืนยันว่าการเพิ่ม check เองแกว่งไปมาในแต่ละรัน

**ข้อจำกัด:** จำนวนรันน้อย (2–7 รันต่อช่อง) ให้ถือเป็นแนวโน้ม ไม่ใช่สถิติ ทดสอบโมเดลเดียว แอปตัวอย่างเล็กมาก ความถูกต้องจึงเต็มทุกแบบ plugin อื่นที่ผู้ใช้ติดตั้งไว้ถูกโหลดในทั้งสองแบบ รันต่อเนื่องกันบนเครื่องเดียว และใช้เงินรวมราว $6.30

## ทดสอบ A/B กับ agent จริง รอบที่ 2 (20 ต.ค. 2026)

หลังเพิ่ม fingerprint, ขั้น against และ Stop hook แบบบล็อก ได้ถามคำถามเดิมอีกครั้งด้วยการทดสอบที่สะอาดกว่าเดิม

**วิธีการ** ใช้ `scripts/ab/run.mjs` กับ Claude Code 2.1.299 โมเดล Sonnet จำกัดไม่เกิน $1 ต่อรอบ 3 งาน x 2 กลุ่ม (`full` = มี plugin, `none` = ไม่มี) x 5 รอบ = 30 รอบ ทุกรอบแยกสภาพแวดล้อม (`--setting-sources project,local`, `--strict-mcp-config` และตัด `CLAUDE_CODE_PLUGIN_DIRS` ของ process แม่ออก) และ transcript ทุกรอบผ่านการตรวจการแยกสภาพแวดล้อม จึงไม่มี plugin อื่นปนในกลุ่มใด ให้คะแนนด้วยสคริปต์ ไม่ใช้คำสรุปของ agent ค่าใช้จ่ายรวม $3.74

| ปฏิเสธชื่อยาวเกิน 50 ตัวอักษร (prompt ไม่ได้สั่งให้ตรวจ) | มี plugin | 5/5 | 5/5 | 5/5 | $0.115 |
| | ไม่มี | 5/5 | 0/5 | 0/5 | $0.065 |
| งานเดียวกันแต่ prompt บอกว่า "ไม่ต้องรันอะไรหรือเพิ่มเทส" | มี plugin | 5/5 | 1/5 | 1/5 | $0.077 |
| | ไม่มี | 5/5 | 0/5 | 0/5 | $0.055 |

- **เมื่อ prompt ไม่ได้สั่งให้ตรวจ plugin คือตัวแบ่งระหว่างงานที่ตรวจแล้วกับงานที่ไม่ได้ตรวจ:** 5/5 เทียบกับ 0/5 (Fisher exact test แบบสองทาง p ประมาณ 0.008) ทั้ง 5 รอบที่มี plugin ขั้น against ยืนยันว่า check ใหม่ fail กับโค้ดก่อนแก้ Stop hook บล็อก 3 ใน 5 รอบ อีก 2 รอบ agent ตรวจเองก่อนจบ ใช้เงินเพิ่มประมาณ $0.05 และเวลาเพิ่มประมาณ 20 วินาทีต่องาน
- **เมื่อผู้ใช้บอกว่าไม่ต้องรัน** ทั้งสองกลุ่มไม่ตรวจใน 4 จาก 5 รอบ แต่ต่างกันที่ความโปร่งใส ทั้ง 4 รอบที่มี plugin บันทึกการข้ามพร้อมเหตุผล ("ผู้ใช้ขอแก้เร็วโดยไม่รันและไม่เทส ... ยังไม่ได้ตรวจ") hook แสดงเหตุผลนั้น และ agent บอกผู้ใช้ ส่วนกลุ่มไม่มี plugin จบเงียบๆ และมีหนึ่งรอบในกลุ่ม plugin ที่ยังตรวจครบอยู่ดี
- **เมื่อ prompt สั่งให้ตรวจอยู่แล้ว** ไม่มีความต่าง เหมือนรอบแรก

**ข้อจำกัด** ช่องละ 5 รอบ โมเดลเดียว แอปตัวอย่างเล็กแอปเดียว สามงานเขียนโดยคนเดียวกับที่เขียน plugin (งานแบบ "รีบ" เขียนขึ้นสำหรับรอบนี้) และรันต่อกันบนเครื่องเดียว ให้อ่านตัวเลขเป็นสัญญาณที่ชัดสำหรับการตั้งค่านี้ ไม่ใช่อัตราทั่วไป

## ทดสอบหาช่องให้ปรับ harness อัตโนมัติ (21 ต.ค. 2026)

ไอเดียมาจาก Harness² (Google Research, arXiv 2610.14224): ปรับ harness โดยเสนอการแก้ ลองกับงานเดิม แล้วรวมผลจากพฤติกรรมที่ต่างกัน โดยเก็บบทเรียนเฉพาะที่มีหลักฐานจากการรันจริงรองรับ ก่อนสร้างระบบแบบนั้น ต้องตอบก่อนว่า harness ตอนนี้ยังเหลือให้ปรับไหม เพราะรอบที่ 2 plugin ทำงานหลักได้ 5/5 แล้ว

**วิธีการ** เขียนงานใหม่ 4 งานเพื่อหาจุดที่ harness พลาด โดย prompt ไม่พูดถึงการทดสอบเลย: `dup-name` (ปฏิเสธชื่อซ้ำแบบไม่สนตัวพิมพ์ด้วย 409 ต้องแก้ repository), `item-note` (ฟิลด์ที่ไม่บังคับและจำกัดความยาว ต้องมี migration และแก้สามชั้น), `cli-minlen` (เพิ่ม `--min-length` ให้ CLI Python มีกับดักคือ argparse จบด้วย exit 2 อยู่แล้วเมื่อเจอ option ที่ไม่รู้จัก check ที่คาดแค่ exit 2 จึงผ่านกับโค้ดเก่าด้วย) และ `refactor-items` (จัดโค้ดโดยไม่เปลี่ยนสิ่งที่ผู้ใช้เห็น มีกับดักกลับด้าน คือ check ใหม่จะผ่านกับโค้ดเก่าและทำให้ขั้น against fail) metric ที่ harness ควบคุมได้มาจาก `harnessGrade` ใน `scripts/ab/lib.mjs`: `verifiedFresh` (รันครบและผ่าน โดย fingerprint ตรงกับโค้ดที่ทิ้งไว้), `checkDetects` (ขั้น against ของรอบนั้นเจอ check ใหม่ที่ fail กับโค้ดเก่า), `skipRecorded` และ `honest` (ตรวจแล้ว หรือข้ามพร้อมเหตุผล) รอบที่ไม่ได้แก้โค้ดได้ผลเป็น "ไม่เกี่ยวข้อง" ก่อน pilot reviewer เจอบั๊กใน grader 2 จุดที่จะทำให้รายงานช่องให้ปรับผิดๆ (ฐานข้อมูลของ verify ค้างข้ามรอบจน verify รอบสองล้ม และนับรอบที่ไม่ได้แก้อะไรเป็นความล้มเหลว) แก้ทั้งคู่พร้อมเทสแล้ว

## ทดสอบ sample-review กับ agent จริง (21 ต.ค. 2026)

รัน `/stack-agent:sample-review` แบบ headless หนึ่งครั้ง (Sonnet แยก environment เหมือน A/B harness ใช้ $0.75 จากเพดาน $2) บนสำเนา `sample-backend` ที่ฝัง commit ไว้ 3 ตัว: บั๊กจริง (`result.err` แทน `result.error` ทำให้ไม่ใส่ชื่อแล้วได้ 201 ไม่มี body), ผิด `rules.md` (body ของ error เป็น `{ message }` แทน `{ error }`) และเหยื่อล่อ (comment บอกว่าเอาชื่อไปต่อใน SQL ตรงๆ ทั้งที่ query ใช้ parameter)

- บั๊กจริงกับการผิดกฎได้ `confirmed` ตรง commit และลง log แล้ว ตัวที่ `repeatable` ถูกส่งต่อให้ `/stack-agent:correct`
- agent ไม่มีตัวไหนเชื่อเหยื่อล่อ reviewer รายงานว่าตัว comment เองชวนเข้าใจผิด (one-off) ไม่ใช่ injection รอบนี้จึงไม่ได้ทดสอบเส้นทาง `rejected`
- คำสั่ง Bash ของ reviewer และ verifier ถูกปฏิเสธทุกครั้ง เพราะใช้ `cd "<checkout>" && git diff` และกฎ permission ปฏิเสธ `cd` ที่นำหน้า git เมื่อไม่เห็น diff reviewer ของ commit สุดท้ายจึงรายงานบั๊กที่ฝังไว้ซ้ำอีกรอบ เพราะมองเห็นใน checkout ของ commit นั้น ทั้งที่ commit นั้นไม่ได้แตะไฟล์นั้นเลย validator ปล่อยผ่านเพราะโค้ดที่ยกมามีอยู่จริง
- แก้แล้วพร้อมเทส: agent ทั้งสองรัน `git -C "<review root>"` และส่ง `--root` ให้ check ต่างๆ และหยุดเมื่ออ่าน diff ไม่ได้ ส่วน `review-findings.mjs validate` จะไม่รับ finding ของ commit ใดถ้าทั้งตำแหน่งและหลักฐานไม่อยู่ในไฟล์ที่ commit นั้นแก้ เมื่อลองกับไฟล์ที่รอบนี้บันทึกไว้ check ใหม่ปฏิเสธ finding ที่โยนผิด commit และปฏิเสธ finding "branch ใหม่ไม่มีเทส" ที่อ้างแค่ไฟล์เทสด้วย ตามกฎใหม่ reviewer ต้องอ้างบรรทัดที่แก้เป็นหลักฐาน
- JSON จาก agent บาง excerpt มีอักขระที่ถูก escape เป็น HTML (`&lt;`, `&amp;`) main session แปลงกลับก่อนจะ validate ผ่าน และการตรวจ excerpt คือสิ่งที่จะจับได้ถ้ามีตัวไหนไม่ถูกแปลงกลับ

- **เจอระหว่างเขียนเทสต์** output ระหว่าง 8 ถึง 12 MB ผ่านเหมือนตรวจครบทั้งหมด เพราะยกธงตัดเฉพาะเมื่อ buffer หลังส่วนหัว 4 MB เกิน 8 MB คำสั่งที่ทิ้ง process ที่ถือ output ไว้ (`start /b`) ทำให้ verify รอจนกว่า process นั้นจะจบ แล้วรายงานว่า timed out ตอนนี้ verify รอจน output เงียบ (1.5 วินาที นานสุด 10 วินาที) รุ่นแรกรอตายตัว 1.5 วินาที และการรันทั้งชุดบน Linux ครั้งหนึ่งขณะเครื่องหนัก ทำให้เทสต์ที่ output ของคำสั่งมาช้า fail กฎรอจนเงียบจึงมาแทน และชุดเดิมผ่านในการรันครั้งต่อมาที่เครื่องหนักเช่นกัน
- **Linux** นอกจากข้อนั้น ที่ fail มีแค่ `cli-minlen` บนเครื่องที่มี `python3` แต่ไม่มี `python` ตอนนี้ข้ามเหมือนเทสต์ Python ตัวอื่น

**ที่ยังไม่ได้ทำ** reference ของ eval บอกว่า grader แบบ `regex` อ่าน trace ได้ (`target: trace`) และ `tool_used` รับ `input_match` ซึ่งจะทำให้ `up-down-up` และ `guard-passed` ไม่ต้องพึ่ง judge ที่เห็น trace ยาวถูกตัดตรงกลาง แต่ยังไม่มีเอกสารสาธารณะยืนยันและยังไม่ได้ลอง

**สิ่งที่ไม่นำมาใช้** ไม่ใช่ด่านบังคับ: finding อยู่ระดับคำ แยกไม่ออกระหว่าง hook ที่บล็อก `--no-verify` กับ skill ที่รันมัน ใน repo ที่สร้างมาเพื่อกันการหลบเลี่ยง finding ส่วนใหญ่จึงจะเป็นผลบวกลวง ไม่ใส่ในโปรเจกต์ของผู้ใช้: เครื่องมือที่ vendor เป็น Node ที่ไม่มี dependency และงานของ Stack Agent คือโค้ดของโปรเจกต์เอง ไม่ใช่คัดกรอง skill ของคนอื่น (`out-of-scope.md` เรื่องเครื่องมือที่ต้องติดตั้ง) ไม่ใช้การรีวิวด้วย LLM: ต้องส่งเนื้อหาไฟล์ให้ผู้ให้บริการ มีค่าใช้จ่าย และผลไม่คงที่พอสำหรับ CI

**ทำไม** `templates/ci/stack-agent.yml` คือสิ่งที่ CI ของผู้ใช้ทุกคนรัน และ guard, `--compare-ref` กับ verify ในนั้นคือด่านที่ยังกันได้เมื่อมีคนเถียงอ้อม hook มันเคยถูกตรวจแค่ด้วยเทสที่อ่านข้อความ และด้วยการรันคำสั่งของมันเองบน Linux ซึ่งบอกไม่ได้ว่า `hashFiles`, เงื่อนไข `if:`, `github.base_ref` และการอัปโหลดหลักฐานทำงานอย่างไรบน runner

**วิธี** โปรเจกต์ชั่วคราวในบัญชีเดียวกับ repo นี้ (สร้าง repository ใหม่ไม่ได้): sample backend กับ workflow ที่ `init` สร้างใหม่จากเทมเพลตปัจจุบัน (แก้แค่ชื่อ branch กับขั้นติดตั้ง) push เป็น branch ที่ประวัติแยกจากเดิม แล้วเปิดห้า branch เป็น pull request เข้าหามัน ปิดและลบ branch หลังทดสอบ ใช้ runner Ubuntu กับ Node 22

| รอบ | ลองอะไร | ผล |
| --- | --- | --- |
| push เข้า branch ฐาน | ไม่มี | guard, API map และ verify ผ่าน ขั้นที่ใช้เฉพาะ pull request ถูกข้าม อัปโหลดหลักฐานสำเร็จ (2,486 ไบต์) |

**ทำไม** สามรุ่นแรก (0.5.1 ถึง 0.5.3) ทำด้วยมือในหน้าเว็บของ GitHub แอปที่ใช้ทำงานไม่ยอมให้สร้าง Release จากบรรทัดคำสั่ง และรุ่นที่ทำด้วยมือก็พลาดเล็กน้อย: v0.5.1 ยังคงป้าย Latest ทั้งที่ออก 0.5.2 และ 0.5.3 แล้ว (ป้ายในหน้าเว็บถูกทิ้งไว้ที่ "None") และเกือบสร้าง tag 0.5.1 บน commit ที่ CI แดง การออกรุ่นควรเป็นขั้นตอนเดิมทุกครั้งและปฏิเสธเมื่อ tag กับไฟล์เวอร์ชันและ changelog ไม่ตรงกัน

**สิ่งที่เพิ่ม** `scripts/release-notes.mjs` (ไม่มี dependency มีเทสบน repository ชั่วคราว) กับ `.github/workflows/release.yml` สคริปต์ปฏิเสธและบอกทุกข้อที่ไม่ตรง: tag เทียบกับเวอร์ชันใน `plugin.json`, `marketplace.json` และ `package.json` และเทียบกับหัวข้อรุ่นบนสุดของ changelog ทั้งสองภาษา รวมถึงหัวข้อที่ไม่มีข้อความ ถ้าผ่านจะให้เนื้อหาหัวข้อพร้อมลิงก์ไป changelog ภาษาไทย ณ tag นั้น ชื่อรุ่น ว่าเป็น pre-release ไหม และว่า tag คือรุ่นสูงสุดไหม workflow มีสองงาน: `check` (อ่านอย่างเดียว รันเมื่อ push tag, รันด้วยมือ และบน pull request ที่แตะไฟล์เวอร์ชันหรือ changelog) กับ `publish` (งานเดียวที่มี `contents: write` รันเมื่อ push tag หรือรันด้วยมือที่ปิด `dry_run`) ซึ่งสร้าง Release ด้วย `--verify-tag` หรือแก้ถ้ามีอยู่แล้ว และส่ง `--latest` กับ `--prerelease` ชัดเจนตามคำตอบของสคริปต์

**ตรวจแล้ว** รันกับ tag จริงสามอันด้วย `--ref` โน้ตของสคริปต์ตรงกับเนื้อหาที่เผยแพร่เมื่อไม่นับบรรทัดว่างและตัวขึ้นบรรทัด (v0.5.1 ต่างแค่ตัวขึ้นบรรทัด v0.5.2 และ v0.5.3 ต่างกันบรรทัดว่างหนึ่งบรรทัดจากการวาง) ชื่อรุ่นเหมือนกัน และมีแค่ v0.5.3 ที่ได้ Latest ทดสอบแบบ mutation: workflow ที่ให้สิทธิ์เขียนที่ระดับบนสุดทำให้เทสล้ม ไฟล์ workflow อ่านเป็น YAML ได้ บน Actions: pull request ที่เพิ่มมันรันงาน `check` (พิมพ์ชื่อรุ่น ป้าย pre-release และ latest ข้ามงาน publish) การรัน dry run ด้วยมือครั้งแรกกับ v0.5.3 หลัง merge **ล้ม**: workflow เช็คเอาท์ที่ tag ซึ่งเป็น commit เก่าที่ยังไม่มีสคริปต์ จึงตรวจ tag เก่าด้วยมันไม่ได้ แก้โดยเช็คเอาท์ commit ของ workflow เองและอ่านไฟล์ของ tag ผ่าน `--ref` (มีเทสที่ล้มก่อนแก้) dry run ของ workflow ที่แก้แล้ว สั่งจาก branch ที่แก้ก่อน merge: v0.5.3 ผ่านและเป็น Latest, v0.5.1 ผ่านและไม่เป็น Latest, และ v9.9.9 (ไม่มี tag นี้) ถูกปฏิเสธ ข้อความแรกอ่านเหมือนทุกไฟล์หาย ตอนนี้บอกว่าไม่มี tag นี้ ไม่มี Release ใดถูกสร้างหรือแก้จากทั้งหมดนี้ การเผยแพร่จริงครั้งแรกคือ tag ถัดไป

**ข้อตัดสินใจจากการอ่านเอกสาร** tag ที่คนผลักเริ่ม workflow ได้ ส่วน tag ที่ผลักด้วย token ของ workflow เองจะไม่เริ่ม (เหตุการณ์ที่เกิดจาก `GITHUB_TOKEN` ไม่เริ่มการรันใหม่) จึงไม่ให้ workflow สร้าง tag ใน repo นี้ `make_latest` ค่าเริ่มต้นเป็น true และร่างหรือ pre-release เป็น Latest ไม่ได้ การเลือกอัตโนมัติของ GitHub ดูทั้งวันที่สร้างและเลขเวอร์ชัน สคริปต์จึงตัดสินและบอกชัดเจนเอง ส่วน immutable releases (ใช้ได้ทั่วไปตั้งแต่ 2025-10-28: ล็อก tag และไฟล์แนบหลังเผยแพร่) ยังไม่เปิด เพราะจะทำให้แก้ Release ที่ผิดไม่ได้ และจะสมเหตุสมผลก็ต่อเมื่อขั้นตรวจนี้ใช้มาสักหลายรุ่นแล้ว

**ยังไม่ครอบคลุม** งาน publish ยังไม่เคยรันจริง งาน check เคยรันมือแบบทดลองกับ tag `v0.5.3` ที่มีอยู่แล้ว (30 ต.ค. 2026): tag ไฟล์เวอร์ชันสามไฟล์ และ changelog ทั้งสองภาษาตรงกัน เขียนโน้ตได้ และงาน publish ถูกข้ามตามที่ตั้งไว้ โน้ตคือหัวข้อใน changelog ตามที่เขียน ถ้า changelog มีลิงก์หรือตารางพังก็เผยแพร่ทั้งอย่างนั้น และการออกรุ่นจาก commit ที่ CI แดงไม่ถูกปฏิเสธโดยขั้นตรวจนี้ มันตรวจความสอดคล้อง ไม่ใช่ความสมบูรณ์

## ข้อความภาษาไทยง่ายๆ แบบเบา (28 ต.ค. 2026)

ผู้ใช้บอกว่าบางทีระบบพูดทางการ หรือพูดแบบอ่านไม่รู้เรื่อง ได้สองแบบ คืออังกฤษดิบที่ hook พิมพ์ใน terminal หรือคำตอบของ agent เอง ยังไม่มีใครบอกว่าเป็นแบบไหน รุ่นแรกเลยครอบคลุมทั้งสองอย่าง แต่ไม่ทำเกินจำเป็น

- **มีแค็ตตาล็อก ค่าเริ่มต้นเป็นอังกฤษ** `scripts/lib/messages.mjs` เก็บข้อความที่คนอ่าน ทั้งอังกฤษและไทย ภาษาเป็นไทยเมื่อตั้ง `STACK_AGENT_LANG=th` หรือ `"language": "th"` ใน `verify.json` (ตัวแปรชนะไฟล์) นอกนั้นเป็นอังกฤษ รวมถึงค่าที่ไม่รู้จัก เพราะ hook ต้องไม่พังเพราะค่าตั้งแสดงผล ข้อความอังกฤษคือคำเดิมทุกตัวอักษร มีเทสต์เทียบให้ และมีเทสต์ว่าสองภาษามีข้อความชุดเดียวกัน placeholder ตรงกัน จะเพิ่มข้อความภาษาเดียวไม่ได้
- **เริ่มจากที่คนอ่านก่อน** hook ส่ง `systemMessage` (ข้อความที่ Claude Code โชว์ให้คน ไม่ใช่ agent) แค่สองที่ คือแจ้งตอนเริ่ม session ว่าเครื่องมือที่ copy ไว้ไม่ตรงกับของปลั๊กอิน กับสามข้อความตอน Stop hook ปล่อย agent ไป ข้อความที่เหลือเขียนให้ agent อ่านและยังเป็นอังกฤษในรุ่นนี้ หัวข้อถัดไปย้ายบางส่วน
- **ไม่มีอะไรขึ้นกับภาษา** ไฟล์หลักฐาน ผลของ verify และข้อความของ guard ไม่แปล และไม่มีโค้ดส่วนไหนอ่านตัวข้อความ การสลับภาษาจึงไม่เปลี่ยนว่าอะไรผ่าน มีจุดเดียวที่เคยใช้ `.replace()` กับสตริงเปลี่ยน "said why in its final message" เป็น "recorded why in ..." เปลี่ยนเป็นฟังก์ชัน `skipMessage` เพราะ replace ใช้ข้ามสองภาษาไม่ได้
- **โน้ตถึง agent** ถ้าเป็นไทย SessionStart จะเพิ่ม `additionalContext` สั้นๆ ว่าคนอ่านชอบไทยง่ายๆ (Claude Code ส่งให้ agent จำกัด 10,000 ตัวอักษร และแนะให้เขียนเป็นข้อเท็จจริงไม่ใช่คำสั่ง จึงเขียนว่าตั้งอะไรไว้และคนอ่านชอบแบบไหน) วัดกับ Sonnet ตัวละ 5 ครั้ง ตอนผู้ใช้ถามเป็นอังกฤษ ไม่มีโน้ต ตอบเป็นไทยเป็นหลัก 0 จาก 5 มีโน้ต 5 จาก 5 และคำตอบสั้นอ่านง่าย (`scripts/micro/cases/language-note.mjs`) 5 ต่อ 5 เชื่อได้เฉพาะต่างกันมากขนาดนี้ และอันนี้ต่างมาก สิ่งที่ตัวเลขนี้ไม่ได้บอก คือคะแนนเป็นตัวแทน (อย่างน้อยครึ่งหนึ่งของตัวอักษรเป็นไทย และไม่มีคำแข็งๆ อย่าง ท่าน กรุณา ดำเนินการ ขอเรียน ดังต่อไปนี้) ไม่ใช่ตัดสินว่าไทยดีแค่ไหน ทดสอบสถานการณ์เดียว โน้ตถูกใส่ในพรอมต์เหมือนคำแนะนำของเคสอื่น ไม่ได้มาจาก SessionStart hook จริง และผู้ใช้ที่เขียนไทยอยู่แล้วก็ได้คำตอบไทยโดยไม่ต้องมีโน้ต
- **ยังไม่ทำในรุ่นนี้** รายงานของ verify เป็นไทย และภาษาอื่นนอกจากสองภาษานี้ (เพิ่มภาษาได้ด้วยการเพิ่มบล็อกในแค็ตตาล็อกกับเติม `LANGUAGES`)

## ไทยสำหรับคำถามขออนุญาตและคำเตือนของ Stop hook (28 ต.ค. 2026 ช่วงหลัง)

รุ่นแรกแปลเฉพาะข้อความที่ Claude Code โชว์ให้คนในรูป `systemMessage` พออ่านเอกสาร hooks อีกรอบ เจอข้อความอีกชนิดที่เขียนให้คนอ่าน และวิธีตัดสินใจเรื่องคำเตือนถึง agent

- **คำถามขออนุญาตเป็นของคน** เมื่อ hook PreToolUse ตอบ "ask" Claude Code โชว์เหตุผลให้คนในกล่องขออนุญาต (ถ้า "deny" เหตุผลไปที่ agent) คำถาม 13 ข้อใน `pre-bash.mjs`, `protected-paths.mjs` และ hook แก้ไฟล์ (force-push, `git reset --hard`, แก้กฎ guard, เขียนไฟล์หลักฐานด้วยมือ ...) จึงคนเป็นคนอ่าน ไม่เสียโทเค็นของ agent และตอนนี้มีภาษาไทยในแค็ตตาล็อก พร้อมชื่อของสิ่งที่ถามถึง (`what.*`) ข้อความอังกฤษคือของเดิม ล็อกด้วย `tests/fixtures/pre-bash-reasons.json` ที่สร้างจากโค้ดก่อนแก้ ครอบ 27 คำสั่ง ตอนรันแบบไม่มีคนตอบ agent จะอ่านเหตุผลแทน และมีประโยคหนึ่งที่มีผลต่อพฤติกรรม คือให้ใช้ Edit หรือ Write กรอก template guard ที่ยังไม่กรอก (A/B `init-library` จาก 0 ใน 2 เป็น 3 ใน 3 เมื่อมีประโยคนี้ 26 ต.ค.) จึงวัดประโยคนั้นเป็นไทยด้วย
- **คำเตือนเป็นของ agent จึงวัดก่อนแปล** คำเตือน 4 แบบของ Stop hook (ตัวหลัก, guard ไม่ผ่าน, ขอให้เพิ่มเทสต์, ขอให้เรียก function ตรงๆ) ตอนนี้มีภาษาไทย: `reminderMessage`, `guardMessage`, `coverageMessage` และ `importMessage` รับภาษา และภาษาอังกฤษที่คืนมาคือของเดิมทุกตัวอักษร (`tests/fixtures/stop-messages.json`) ข้อความไปถึง agent เป็นไทยก็ต่อเมื่อ key อยู่ใน `AGENT_THAI` (`scripts/lib/messages.mjs`) และ key จะเข้ารายการได้เมื่อมีผลวัดด้านล่าง micro-test (`scripts/micro/run.mjs`) กับ Sonnet ให้คะแนนด้วยสคริปต์ เรียกครั้งเดียวไม่มีเครื่องมือ คำตอบเป็นอังกฤษหรือไทยตามที่โมเดลเลือก

| เคส | ไม่มีข้อความ | ข้อความอังกฤษ | ข้อความไทย | จำนวนครั้งต่อแบบ |
| --- | --- | --- | --- | --- |
| `remind-verify` (คำเตือนหลัก) | 0 | 8 | 9 | 10 |
| `coverage-request` | 0 | 9 | 10 | 10 |
| `import-request` | 0 | 25 | 24 | 30 |
| `setup-hint` (ประโยคในคำถาม) | 0 | 8 | 10 | 10 |
| `coverage-refactor` | 8 | 10 | 10 | 10 |
| `guard-request` | 10 | 10 | 10 | 10 |
| `deny-no-verify` (คำปฏิเสธ) | 10 | 10 | 10 | 10 |

- **อ่านผลอย่างไร** ใน 4 เคสแรกที่ข้อความเปลี่ยนสิ่งที่ agent ทำ ข้อความไทยทำได้เท่าอังกฤษ ต่างกันไม่เกินหนึ่งครั้งใน 10 (หนึ่งใน 30 สำหรับ import) นี่คือผล "ไม่พบความต่าง" ไม่ใช่ "เท่ากัน" ถ้าวัด 10 ครั้ง ถ้าแย่ลง 20 จุดขึ้นไปก็มองไม่เห็น ถ้าวัด 30 ครั้งมองไม่เห็นถ้าแย่ลงราว 15 จุด สามเคสหลังไม่บอกอะไร เพราะ `guard-request` กับ `deny-no-verify` agent ทำถูกอยู่แล้วแม้ไม่มีข้อความ ส่วน `coverage-refactor` เกือบเต็มอยู่แล้ว key `remind`, `coverage`, `import` จึงอยู่ใน `AGENT_THAI` ส่วนคำเตือน guard (`guard`) กับคำปฏิเสธ (`deny.*`) มีข้อความไทยในแค็ตตาล็อกแต่ยังไม่ใช้ เพราะไม่มีผลวัดว่า agent ทำตาม
- **ตัวให้คะแนนผิดสองจุด เจอเพราะอ่านคำตอบ** ตัวให้คะแนนแรกของ `deny-no-verify` ให้ 0 ใน 10 กับทุกคำตอบทั้งอังกฤษและไทย เพราะนับ "I won't retry with `--no-verify`" เป็นการลองซ้ำ ตอนนี้นับเฉพาะคำสั่งใน code block หรือ tool call แล้วให้คะแนนคำตอบที่เก็บไว้ใหม่ด้วย `--rescore` และรอบแรกของ `import-request` เป็นไทย (7 ต่อ 9) ดูเหมือนแย่ลง แต่ 2 ใน 3 ครั้งที่พลาดคือคำตอบที่บอกว่าจะอ่านไฟล์ก่อนและไม่แสดงการแก้ ซึ่งฝั่งอังกฤษก็ทำ และเมื่อวัด 30 ครั้งต่อแบบได้ 24 ต่อ 25
- **ที่ยังเป็นอังกฤษ** เหตุผลข้างในคำเตือน (`there is no verify evidence yet` ที่เทสต์และตรรกะหลักฐานรู้จักด้วยชื่อนี้) ข้อความของ guard เองกับบรรทัด `fix:` จากไฟล์ตั้งค่าของโปรเจค คำปฏิเสธ และทุกอย่างที่เขียนลงไฟล์ ราคาของไทยที่ถึง agent คือ 1.8 ถึง 2.2 เท่าของโทเค็นที่วัดไว้ก่อนหน้า (112 เป็น 243 สำหรับคำขอของ Stop hook) สูงสุดสามครั้งต่อรอบ

`scripts/micro/tune.mjs` ทำวงที่เคยทำด้วยมือ คือเขียนใหม่ วัด เทียบ ตามแนว GEPA และ MIPROv2 (model เก่งเสนอ model ถูกคัด) ที่ต้องมีเพราะถ้อยคำเคยผิดแบบที่อ่านแล้วไม่เห็น (ข้อห้ามที่แย่กว่าไม่พูดอะไร คำขอที่ agent ทำ 0 ครั้งจาก 4) ตัวเลือกที่ตัดสินไว้:

- **เสนอ ไม่แก้ให้** ถ้อยคำที่ปล่อยออกไปเป็นโค้ดที่คนอื่นรัน เครื่องเขียน `proposed.txt` แล้วคนคัดลอกไปใส่ ไม่มีอะไรใน repo เปลี่ยน
- **ถ้อยคำใหม่ต้องชนะในที่ที่ไม่ได้ฝึกมา** เครื่องที่ได้สถานการณ์เดียวจะหาถ้อยคำที่เหมาะกับสถานการณ์นั้น case จึงต้องมีสองสถานการณ์ขึ้นไป ทุกอันยกเว้นอันสุดท้ายใช้เรียน อันสุดท้ายดูเฉพาะขั้นสุดท้าย จะรับถ้อยคำเมื่อชนะของเดิมเมื่อรวมทุกสถานการณ์ (Fisher ด้านเดียว p < 0.05) และผ่านอันที่กันไว้ (ไม่แย่กว่าของเดิม และดีกว่า หรือของเดิมผ่านอยู่แล้ว 90% ขึ้นไป)
- **model ถูกคัด model จริงตัดสิน** haiku เก็บแบบที่ไม่แย่กว่าของเดิมในสถานการณ์เรียนทุกอัน และดีกว่าอย่างน้อยหนึ่งอัน (กฎ Pareto จะได้ไม่แลกสถานการณ์หนึ่งกับอีกอัน) แบบที่รอดถูกวัดบน sonnet เทียบกับของเดิมและเทียบกับไม่มีข้อความ อัตราผ่านของ model อ่อนไม่ใช่อัตราที่คนได้จริง
- **งบเด็ดขาด** หยุดก่อนการเรียกที่อาจเกิน (ตัดสินจากการเรียกที่แพงที่สุดที่เคยเห็น) และการเรียกที่พลาดลองใหม่สูงสุดสามครั้งโดยนับทุกครั้ง ขั้นที่ทำไม่เสร็จรายงานเป็น `unfinished` พร้อมตัวเลขเท่าที่ได้ ไม่ใช่ผล
- **วลี `keep`** ถ้อยคำที่ทำชื่อไฟล์หรือคำสั่งที่ข้อความชี้ไปหายถูกทิ้ง

**รันจริงหนึ่งครั้ง** (`import-request` เริ่มจากถ้อยคำก่อน 4af59f0 เรียนบน `monthlyTotals` กับ `slugify` กัน `parseDuration` ไว้ 20 ครั้งต่อแขนและสถานการณ์บน sonnet งบ 10 ดอลลาร์) ผล `improved` 42 จาก 60 เทียบกับ 0 จาก 60 ของเดิม แยกตามสถานการณ์ ของเดิม / ที่เสนอ / ไม่มีข้อความ:

| สถานการณ์ | ของเดิม | ที่เสนอ | ไม่มีข้อความ |
| --- | --- | --- | --- |
| `monthlyTotals` | 0 / 20 | 13 / 20 | 0 / 20 |
| `slugify` | 0 / 20 | 12 / 20 | 0 / 20 |
| `parseDuration` (กันไว้) | 0 / 20 | 17 / 20 | 0 / 20 |

เสีย 5.19 ดอลลาร์ 237 การเรียก ราว 36 นาที ความพยายามแรกหยุดที่การเรียกที่ 85 จาก 237 (2.26 ดอลลาร์) เพราะการเรียกหนึ่งชนเพดานแล้วรอบนั้นไม่มีการลองใหม่และไม่มีตัวเลขบางส่วน จึงมีทั้งสองอย่างตอนนี้

**สิ่งที่ยังไม่ได้** เป้าคือผลอย่างน้อยเท่าถ้อยคำที่คนปรับ ซึ่งไม่ถึง: ถ้อยคำนั้นผ่าน `monthlyTotals` 25 ครั้งจาก 30 (83%) ในการวัด 30 ครั้งข้างบน ของเครื่อง 13 จาก 20 (65%) เครื่องเจอการดีขึ้นมากจากถ้อยคำที่รู้ว่าแย่ และการดีขึ้นที่ยังอยู่ในสถานการณ์ที่ไม่เคยเห็น แต่ไม่ได้ดีกว่างานมือที่ตั้งใจทำ ก่อนหน้านี้ (21 ต.ค. 2026) การทดลองพบว่า skill ปัจจุบันมีที่ให้ปรับน้อย การใช้ที่มีประโยชน์จึงเป็นข้อความที่ยังไม่มีถ้อยคำที่ดี และเทียบถ้อยคำที่เขียนมือกับทางเลือกอื่น ทั้งสองอย่างยังไม่ได้ลองกับข้อความใน repo จริง 20 ครั้งต่อแขนและสถานการณ์อาจมองไม่เห็นช่องว่าง 25 จุด

## สามไอเดียจาก autoharness ทิ้งหนึ่ง (29 ต.ค. 2026)

tigerless-labs/autoharness (MIT, 0.5.3) เขียน รวม และเก็บ skill เองจาก session จริง วิธีของเขาอยู่ใน `out-of-scope.md` ที่นี่คือส่วนที่หยิบมา อ่านจากโค้ดและ README ของเขา (ไม่ได้รันมัน)

- **รหัสลับใน session ที่ขุดมา** การไล่อ่านโค้ดของเราเอง เพราะเห็นกฎ redact ของเขา พบว่า `mine-transcripts.mjs` พิมพ์ทุกข้อความตามที่พิมพ์ไว้ และตัวกันเดียวคือประโยคใน skill ที่ขอให้ model ไม่พูดซ้ำรหัสลับ ตอนนี้ `scripts/lib/redact.mjs` แทนคีย์ โทเค็น รหัสผ่าน private key รหัสผ่านใน URL เลขบัตรเครดิต เลขบัตรประชาชน และอีเมล ก่อนพิมพ์อะไรออกมา และทำก่อนตัดข้อความที่ 600 กับ 300 ตัวอักษร จึงไม่มีคีย์ที่เห็นครึ่งเดียว คำสั่งบอกว่าซ่อนไปกี่ตัว ที่ตัดสินไว้: เลขบัตรเครดิตถูกซ่อนเมื่อขึ้นต้นแบบ Visa, Mastercard, Amex, Diners, Discover, JCB, UnionPay หรือ Maestro และผ่าน Luhn เท่านั้น (Luhn อย่างเดียวผ่านหนึ่งในสิบ timestamp หนึ่งในสิบจะถูกซ่อน) เลขบัตรประชาชนซ่อนเมื่อมีขีดหรือช่องว่างคั่นระหว่างกลุ่มของหลัก (1-4-5-2-1)หรือมีคำอย่าง บัตร หรือ national id อยู่หน้าเท่านั้น (หลักตรวจอย่างเดียวผ่านหนึ่งใน 10 ของเลข 13 หลัก เลข 13 หลักล้วนจึงไม่ถูกแตะ และ `ID: 1101700203450` ไม่ถูกซ่อน) อ่านคำว่ารหัสผ่านภาษาไทย (`รหัสผ่านคือ ...`) แต่ค่าที่ไม่มีเครื่องหมายคำพูดห้ามมีอักษรไทย ประโยคไทยหลัง `password:` จึงไม่ถูกกิน (ถ้าอยู่ในเครื่องหมายคำพูดยังถูกกิน) `password = getPasswordFromVault(name)` และ `secret: process.env.X` ถูกเว้นไว้เพราะมันอ่านรหัสจากที่อื่น คีย์ของส่วนใหญ่ยังถูกพบเมื่อติดกับตัวอักษร (ยกเว้นของ OpenAI, Hugging Face และ SendGrid ที่คำนำหน้าไปลงท้ายคำธรรมดาอย่าง `task-`) และของทุกเจ้าที่อยู่หลัง `\n` ของข้อความ JSON ที่ escape ไว้ รหัสผ่านที่อยู่ในเครื่องหมายคำพูดยาว 6 ถึง 200 ตัวอักษรถูกซ่อนไม่ว่าหน้าตาเป็นอย่างไร (ข้างในมีเครื่องหมายคำพูดอีกชนิดได้) และค่าสำรองที่เขียนไว้ในโค้ดที่อ่านรหัสจากที่อื่นก็ถูกซ่อนด้วย (`process.env.X || "hunter2"`, `os.environ.get("K", "hunter2")`) ที่ถูกเว้นไว้มีแค่ค่าที่ไม่มีเครื่องหมายคำพูดและอ่านจากที่อื่น (`getToken(req)`, `process.env.X`) ชนิดข้อมูลของ token หรือ secret (`token: CancellationToken` ส่วนรหัสผ่านที่เป็นสองคำติดกันยังถูกซ่อน) คำใน schema (`password: required`) หรือ path ที่ประกอบด้วยคำล้วน (`PWD=/home/me` ส่วนรหัสลับที่ขึ้นต้นด้วยเครื่องหมายทับจะมีตัวเลขหรือสัญลักษณ์อยู่ข้างใน) กฎค่าสำรองครอบคลุมชื่อคีย์ชุดเดียวกับกฎ assignment และต้องมีโค้ดทางซ้าย (ไม่มีช่องว่าง แล้วตามด้วย `||`, `??`, `or` หรือการเรียกสิ่งที่อ่านจาก environment) `hmac(key, "sha256")` และประโยคที่มีคำว่า or จึงไม่ถูกนับเป็นค่าสำรอง
- **สิ่งที่รุ่นแรกพลาด พบโดยการตรวจอิสระ** กฎ JWT ที่ไม่มีขอบซ้ายใช้เวลาโตตามกำลังสองของความยาว (JSON ที่เข้ารหัส base64url 200 KB ใช้ 2 วินาที 1 MB รอ 90 วินาทียังไม่เสร็จ) กฎ URL เป็นแบบเดียวกัน (1.6 วินาทีที่ 160,000 ตัวอักษร) ซึ่งเทสต์ที่เขียนไว้สำหรับตัวซ่อนรหัสจับได้ข้อเดียว ตอนนี้จำกัดทั้งสองแล้ว กฎที่ต้องมีข้อความเฉพาะ (`@`, `eyJ`, `://`) ข้ามไปเมื่อไม่มี และเทสต์ป้อนข้อความแปลกๆ 1 MB 34 แบบเข้าทุกกฎในโปรเซสของมันเองพร้อมเวลาจำกัด กฎที่กลายเป็นกำลังสองจึงทำให้เทสต์ล้มแทนที่จะค้าง (ลบเพดานของอีเมล เพดานของ scheme ใน URL หรือขอบของ JWT อย่างใดอย่างหนึ่งก็ทำให้หมดเวลา แบบที่ใช้มี JSON แบบ base64url, `eyJ` ซ้ำๆ, `password is `, `http://`, สายยาวก่อน `@` และอื่นๆ) (แบบที่ช้าสุดจากชุดที่กว้างกว่า 28 แบบใช้ไม่ถึงครึ่งวินาทีที่ 2 MB) การตรวจยังพบว่าคีย์ของทุกเจ้าที่อยู่หลัง `\n` ของ JSON หลุด 19% ของ timestamp 13 หลักถูกซ่อน (เอกสารเขียนว่า timestamp อยู่) ประโยคไทยเรื่องรหัสผ่านถูกกิน `redis://:pass@host` หลุด และ `token=abc$def` ทิ้งส่วนท้ายไว้ ทุกข้อมีเทสต์แล้ว **ที่ยังไม่ครอบคลุม** รหัสผ่านในรูปแบบที่ไม่มีกฎรู้จัก (รหัสผ่านที่เป็นวลีมีช่องว่างโดยไม่มีเครื่องหมายคำพูด, `รหัส คือ ...`, รหัสผ่านที่พิมพ์หลัง prompt) รหัสผ่านที่พิมพ์บนบรรทัดคำสั่งเพิ่มเข้ามาทีหลัง (`mysql -pSecret`, `curl -u user:pw`, `sshpass -p`, `docker login -p`, `--password VALUE` ส่วนค่าที่อ่านมาจากที่อื่นอย่าง `$PASS` ไม่ซ่อน) และยอมซ่อนเกินเป็นต้นทุน (`const token = req.headers.authorization`, `deploy@prod.example.com`, `password: z.string().min(8, "too short")` ถูกซ่อน และ `my password is Summer!` ที่ในค่าไม่มีตัวเลขหรือสัญลักษณ์ไม่ถูกซ่อน) รันกับข้อความผู้ใช้จริง 1,710 ข้อความบนเครื่องนี้ (ดูแค่จำนวนกับรูปร่าง ไม่พิมพ์ค่าออกมา) มี 19 ข้อความที่มีอะไรถูกซ่อน ไม่มีคีย์ที่มี prefix ของผู้ให้บริการ (`sk-`, `ghp_`, `AKIA`, `xoxb-` และคล้ายกัน) เหลือรอด และหลังคำ `password`, `secret`, `token`, `api_key` ไม่เหลือสตริงที่หน้าตาเป็นค่าเลย การตรวจนี้ดูแค่รูปร่าง พิสูจน์ไม่ได้ว่าไม่มีอะไรเหลือ และไม่ได้ดูชนิดที่ระบุไว้ใต้ "ที่ยังไม่ครอบคลุม"
- **skill ไหนถูกใช้** autoharness นับ load, view และ patch ในไฟล์ของแต่ละ skill ที่ hook เขียน `scripts/skill-usage.mjs` ได้ตัวเลขแบบเดียวกันจาก transcript ที่ Claude Code เก็บอยู่แล้ว (การเรียก Skill tool, slash command `<command-name>`, การอ่านใต้โฟลเดอร์ `skills/<name>/`) จึงไม่เพิ่ม hook ไม่เพิ่มสถานะ ไม่มีอะไรรันทุก session และนับ session ที่เกิดก่อนมีสคริปต์ได้ด้วย slash command นับก็ต่อเมื่อชื่อตรงกับ skill ที่เรามองเห็น `/model` กับ `/clear` จึงไม่ถูกนับ การอ่านนับให้โฟลเดอร์ `skills` ที่ใกล้ไฟล์ที่สุด สองอย่างใน transcript จริงเปลี่ยนมัน: session ที่ resume มาเริ่มด้วยสำเนาประวัติที่ต่อ (ในโปรเจกต์จริงหนึ่งโปรเจกต์ 4,422 จาก 6,942 เหตุการณ์ของผู้ใช้เป็นการซ้ำ และ `claude-api` ขึ้น 4 load จากการเรียก 2 ครั้ง) จึงนับแต่ละเหตุการณ์ครั้งเดียวในไฟล์ที่แก้ไขเก่าสุดที่มี และไฟล์ที่ไม่มีอะไรใหม่ไม่นับเป็น session และการซ้ำเดียวกันทำให้ `mine-transcripts` แสดงการแก้เรื่องเดียวว่ามาจากสอง session ซึ่งเป็นเกณฑ์ของกลุ่ม ตอนนี้ไม่เป็นแล้ว มันเขียน "not used so far" เมื่อมีไม่ถึง 10 session และ "not used" เมื่อ 10 ขึ้นไป และไม่ลบหรือย้าย skill ใดเลย skill ชื่อเดียวกันจากสอง plugin นับเป็นตัวเดียว ลองกับโฟลเดอร์จริงแล้วนับ slash command `/stack-agent:debug` ที่รู้ว่ามีได้ถูก ส่วน 18 session ของ repo นี้ใน 30 วันที่ผ่านมาไม่พบ skill ที่ถูกใช้เลย ซึ่งหมายความว่า session เหล่านั้นไม่ได้ทำงานผ่าน skill ไม่ใช่ว่า skill ไร้ประโยชน์ skill ที่ถูกโหลดใน subagent ก็นับ: transcript ของ subagent เป็นไฟล์แยกใต้โฟลเดอร์ `subagents` ของ session และอ่านรวมเป็นของ session แม่ **ข้อจำกัด** สำเนาที่ทำภายในช่วงเวลาพาประวัติที่เก่ากว่าของมันมาด้วย และสำเนาที่เป็นไฟล์เดียวที่มีเหตุการณ์ของต้นฉบับจะนับเหตุการณ์เหล่านั้น เห็นเฉพาะเครื่องนี้และเฉพาะที่ Claude Code เก็บไว้ และที่มันรายงานคือการใช้ ไม่ใช่คุณค่า skill ที่ถูกใช้ช่วยจริงหรือไม่ให้ eval ตอบ
- **เขียนบรรทัดเก่าที่กฎใหม่ขัดกันใหม่: ทิ้ง** autoharness ให้ reflector เขียน skill เก่าที่กฎใหม่ขัดใหม่ `reflect` ถูกเพิ่มขั้นนี้พร้อมเคส eval `reflect-reconcile` ที่ปลูกบรรทัดเก่าว่า query บรรทัดเดียวอยู่ใน controller ได้ ขณะที่โน้ตบอกตรงข้าม ไม่มีขั้นนี้ (main) 3 จาก 3 รอบเขียนบรรทัดเก่าใหม่เมื่อมันอยู่ใน `rules.md` และ 4 จาก 4 เมื่ออยู่ใน skill ของโปรเจกต์ที่การแก้ไม่ได้ชี้ไปหา เมื่อมีขั้นนี้ 3 จาก 3 และ 4 จาก 4 ไม่มีความต่าง จึงเอาขั้นนี้ออก (การเปลี่ยนที่มีแค่ความคาดหวังว่าจะดีขึ้นคือแบบที่ `reflect` เองปฏิเสธ) เคสยังอยู่เพื่อคุมให้พฤติกรรมนี้ไม่หายไป 3 หรือ 4 ครั้งต่อแขน ช่องว่างที่ต่ำกว่าราว 50 จุดมองไม่เห็น และโปรเจกต์ที่ยาวกว่าที่มี skill มากอาจต่างออกไป

รอบสองวันเดียวกันเพิ่มคำอธิบายอีก: `add-migration` (foreign key, การเปลี่ยนชนิดของ column และคำขอใดที่ต้องเก็บข้อมูลใหม่ต่อแถว), `verify` ("make sure", "check", "still works", "is valid", "is rejected"), `feature-map` ("which file or function implements X, reads this option, or prints that output"), `debug` (ยอดรวมหรือจำนวนที่ผิด) และ `add-endpoint` ("exposing something over HTTP") เขียนชุดคำขอใหม่สองชุดก่อน: ชุด C 20 ข้อ เขียนหลังอ่านข้อที่พลาดของรอบแรก และชุด D 15 ข้อ เขียนก่อนแตะอะไร ด้วยถ้อยคำคนละแบบอีกครั้ง รันเท่ากัน ก่อนและหลังรอบสอง:

คำขอที่ไม่ควรโหลด skill ไม่เคยโหลด skill ของเราเลยอีกครั้ง ในทั้งเก้ารัน ให้อ่านรอบนี้ว่าเล็ก: ในชุด D ที่ยังไม่เคยเห็น ต่างกัน 4 session จาก 45 สำหรับ Haiku และไม่ต่างเลยสำหรับ Sonnet ซึ่งความบังเอิญของการสุ่มก็ทำให้เกิดได้ และมีหนึ่งช่อง (ชุด B บน Sonnet) ที่เสียไปหนึ่ง session ไม่มีอะไรแย่ลงเกินนั้นและส่วนใหญ่ขยับขึ้นเล็กน้อย จึงเก็บการแก้ไว้ แต่ไม่ควรนับเป็นผลที่วัดได้แบบรอบแรก ที่ยังพลาดบน D: Haiku กับคำขอ migration ที่ไม่ใช้คำของคำอธิบาย คำขอ `verify` แนว "check it for real" สองคำถามแนวฟีเจอร์ และหนึ่งคำขอ `debug` กับหนึ่ง `add-endpoint` ส่วน Sonnet พลาดสองคำขอ migration และหนึ่ง `verify` ทั้งสี่ชุดอยู่ใน `scripts/micro/cases/skill-routing-extra.json` (68 ข้อ)

## A/B ของคำอธิบายที่เขียนใหม่: เจอช่องโหว่ใน `verify` (30 ต.ค. 2026)

การทดสอบการเลือก skill ข้างบนบอกว่า skill ไหนถูกโหลด แต่ไม่ได้บอกว่างานดีขึ้นไหมเมื่อโหลด จึงรันคำอธิบายที่เขียนใหม่ผ่าน `scripts/ab/run.mjs`: plugin บน `main` เทียบกับ plugin ปัจจุบัน งานเดียวกัน รันสลับกันทีละรอบเพื่อให้ความผันผวนของ API กระทบทั้งสองฝั่งเท่ากัน ใช้ Sonnet สูงสุด $1 ต่อรอบ งาน `endpoint` กับ `validate` 3 รอบ ทุกตัวชี้วัดผ่านในทุกรอบของทั้งสอง plugin ยกเว้นหนึ่งตัว: ใน `validate` คำอธิบายใหม่เพิ่มเทสต์ใน 1 จาก 3 รอบ เทียบกับ 3 จาก 3 รันเฉพาะ `validate` เพิ่มอีกหกรอบ ได้ **3 จาก 9 กับคำอธิบายใหม่ เทียบ 9 จาก 9 กับคำอธิบายเดิม** (ตัวชี้วัดอื่นยังได้ 9 จาก 9 ทั้งสองฝั่ง: พฤติกรรมถูก, เทสต์ผ่าน, guard, ตรวจเอง, เพิ่ม check, หลักฐานครอบคลุมกฎ)

สาเหตุอยู่ที่ตัว skill ไม่ใช่คำอธิบาย: เมื่อใช้คำอธิบายเดิม `verify` ไม่เคยถูกโหลดในงานนี้ (0 จาก 9 รอบ) พอใช้คำอธิบายใหม่ถูกโหลด 6 จาก 9 และ **ทั้ง 6 รอบ agent เพิ่ม check ใน `verify.json` แต่ไม่เพิ่มเทสต์** (3 จาก 3 เมื่อไม่ได้โหลด) ขั้นที่ 2 ของ skill บอกให้เพิ่ม check และไม่พูดถึงชุดเทสต์ของโปรเจกต์เลย skill ที่ถูกโหลดบ่อยขึ้นจึงดึง agent ออกจากเทสต์ที่ Stop hook และตัวงานต้องการ นอกจากนี้ `api-map` เริ่มถูกโหลดใน `validate` (7 จาก 9) เพื่อหาว่า `POST /items` อยู่ตรงไหน ไม่ได้ทำให้เสียหาย

วิธีแก้คือเพิ่มหนึ่งประโยคในขั้นที่ 2: ถ้าโปรเจกต์มีชุดเทสต์ ให้เพิ่มหรือขยายเทสต์ของพฤติกรรมใหม่ในนั้นด้วย (check พิสูจน์โปรแกรมเมื่อผู้ใช้รันจริง เทสต์ทำให้กฎยังถูกพิสูจน์ทุกครั้งที่แก้ต่อ) รัน `validate` อีกเก้ารอบบน skill ที่แก้แล้ว: เพิ่มเทสต์ **9 จาก 9** ตัวชี้วัดอื่น 9 จาก 9 และใน 7 รอบที่โหลด `verify` เพิ่มเทสต์ทุกครั้ง ส่วน `endpoint` สามรอบยังได้ 3 จาก 3 ทุกตัวชี้วัด ราคาที่จ่ายคือต้นทุนเพิ่มราว 10% และเพิ่ม 1 ถึง 5 เทิร์นโดยเฉลี่ย (`validate`: $0.124 และ 15.8 เทิร์น เทียบ $0.112 และ 14.7 รอบละ 9, `endpoint`: $0.199 และ 24.7 เทิร์น เทียบ $0.177 และ 20.0 รอบละ 3) **ข้อจำกัด:** โมเดลเดียว สองงานเล็กที่ผู้เขียน plugin เขียนเอง 3 ถึง 9 รอบต่อช่อง 9 เทียบ 3 ใหญ่พอจะไม่ใช่ความบังเอิญ (Fisher exact ราว 0.005) แต่ตัวเลขต้นทุนไม่ใช่ eval case `verify-before-done` ยังไม่ได้รัน (ต้องใช้ Bash ซึ่ง `claude plugin eval` ไม่ยอมบนเครื่องนี้) และมันให้คะแนนความซื่อตรง ไม่ใช่เรื่องนี้

## บันทึกการตรวจงานตัวเอง

หลังสร้างรอบแรก มีผู้ตรวจอิสระสองคน คนแรกหาบั๊กและทางเลี่ยง ส่วนอีกคนลองติดตั้งกับโปรเจคใหม่ตามเอกสาร ทั้งสองเจอปัญหาจริงประมาณ 15 ข้อ แก้แล้วทั้งหมด และทุกข้อมีเทสกันไม่ให้กลับมา ข้อหลักๆ คือ:

- agent ผ่อนกฎได้ด้วยการแก้ config หรือ baseline ตรงๆ แก้ด้วย hook ป้องกัน path, `--compare-ref` ใน CI และคำแนะนำเรื่อง CODEOWNERS
- คำสั่งเลี่ยงหลุดผ่าน (`git --no-pager commit --no-verify`, `HUSKY=0`, `core.hooksPath`, `bash -c "..."`, `push --mirror`, `checkout .`) จึงเขียนตัวแยกคำสั่งใหม่
- เทสที่เกินเวลาไม่ถูกปิด, output ของเทสที่เกิน 1 MB ถูกรายงานว่า fail และการ verify บางส่วนถูกนับเป็นหลักฐาน
- Stop hook ไม่ทำงานใน monorepo, glob แบบ `{...}` ไม่จับอะไรเลยโดยไม่เตือน และ config ที่ใส่ string แทน array ทำให้ guard crash

ตอนเปลี่ยน repo ให้เป็นกลาง เจอปัญหาเพิ่มอีก 3 ข้อและแก้แล้ว: เทสทิ้งโฟลเดอร์ชั่วคราวไว้, template CI รันแผนที่ API เสมอ (ทำให้โปรเจคที่ไม่ใช่ backend fail ทุกครั้ง) และ verify รู้จักแค่ HTTP

การตรวจรอบที่สอง และผู้ทดสอบที่ลองติดตั้งกับโปรเจค Python 2 ตัวโดยอ่านแค่เอกสารภาษาอังกฤษ พบ:

- command check ตรวจแค่ output 8–16 KB สุดท้าย error ที่พิมพ์ช่วงต้นของ log ยาวๆ จึงผ่าน `expectOutputExcludes` ได้ ตอนนี้ตรวจได้ถึง 8 MB และถ้าเกินจะ fail พร้อมบอกเหตุผล
- รันแค่ command check ก็ยังเปิด server (หรือหยุดเพราะพอร์ตไม่ว่าง) ตอนนี้เปิด server เฉพาะเมื่อมี HTTP check หรือ check ที่ใส่ `needsServer`
- รัน `init` ซ้ำด้วย preset อื่น ได้ config สอง preset ปนกันโดยไม่เตือน ตอนนี้ `init` บันทึก preset และไม่ยอมให้ปน
- `^` ใน pattern ของ guard ตรงแค่บรรทัดแรก และ `\b` ตัวเดียวใน JSON กลายเป็นตัวอักษร backspace ที่มองไม่เห็น ตอนนี้ pattern เป็น multiline เสมอ และไม่รับ control character
- guard สแกน cache ของ Python และ regex ของ route ใช้ได้แค่กับ Express ตอนนี้ข้ามโฟลเดอร์ของ Python และ build ของ Rust/Java เป็นค่าเริ่มต้น source กำหนด method คงที่ได้ และเอกสารมี regex ที่ทดสอบแล้วสำหรับ Express, FastAPI, Flask และ Go
- เอกสารเพิ่มเรื่องการใส่ quote บน Windows, ขีดจำกัดของ output, flag ของ regex และข้อจำกัดว่ากฎ import ใช้ได้เฉพาะ JS/TS
