# Writing agent briefs

An agent brief is the comment (or, in a local tracker, the section under `## Comments`) that triage posts when an item becomes `ready-for-agent`. It is the contract an agent works from later, possibly with no one around to ask. The original report and the discussion are background; the brief wins where they disagree.

The brief says what the agent must do. For an issue, that means building the change. For a pull request, it means what is left to do on the existing diff: finish it, close gaps, address review points. The rules are the same for both; the pull-request example below shows the difference.

Start the comment with the triage disclaimer line from `SKILL.md`, then the brief.

## 1. Rules

### Last through refactors

An item can sit in `ready-for-agent` for weeks, and the code will move meanwhile. A brief that names a file and line is wrong the day someone renames the file. Write it so it is still true after files move.

- Describe behavior, interfaces, types and data shapes.
- Name the types, function signatures or config shapes the agent should look for or change.
- Do not give file paths or line numbers.
- Do not assume the current internal structure stays.

### Say what, not how

Describe what the system must do. The agent reads the code fresh and picks the implementation.

- Good: "`ReportOptions` accepts an optional `since` field holding a date."
- Bad: "Open the options file and add a `since` field around line 42."
- Good: "Running `report list` with no arguments prints the ten most recent reports."
- Bad: "Add a `switch` to the main handler."

### Acceptance criteria an agent can check

The agent must know when it is finished. Write each criterion so one command or one observation settles it, and so it can be checked without the others.

- Good: "`report list --since 2025-01-01` prints only reports dated on or after that day."
- Bad: "Filtering should work properly."

### Scope boundary

List what is not part of this item. Without it, an agent will tidy adjacent code or build the next feature.

### Facts, not guesses

If triage confirmed the claim (reproduced the bug, ran the diff), say what was seen: the command or input and the observed result, without paths. If it could not be confirmed, say that too, so the agent starts by checking.

## 2. Template

```markdown
> *This was generated by AI during triage.*

## Agent Brief

**Category:** bug / enhancement
**Summary:** one line saying what must happen

**Current behavior:**
What happens now. For a bug, the broken behavior and how it was seen.
For an enhancement, the existing behavior the new work builds on.

**Desired behavior:**
What must be true when the work is done, including edge cases and errors.

**Key interfaces:**
- `TypeName`: what changes and why
- `functionName()` return type: what it returns now and what it should return
- Config shape: any new option

**Acceptance criteria:**
- [ ] Specific, checkable criterion 1
- [ ] Specific, checkable criterion 2
- [ ] Specific, checkable criterion 3

**Out of scope:**
- A thing that must not change in this item
- An adjacent feature that is a separate item
```

For `ready-for-human`, use the same shape and add a **Why this is not for an agent** line.

## 3. Examples

### Good brief (bug)

```markdown
> *This was generated by AI during triage.*

## Agent Brief

**Category:** bug
**Summary:** CSV export drops the last row when the row count is an exact multiple of the page size

**Current behavior:**
Exporting a report writes rows in pages of 100. With exactly 200 rows, the
file holds 199 data lines. With 201 or 199 rows, the file is complete.
Reproduced with a 200-row report: the output ended one line short.

**Desired behavior:**
Every row appears exactly once in the export, for any row count, including
zero and exact multiples of the page size.

**Key interfaces:**
- The `ExportOptions` type needs no change.
- The code that walks the pages and decides when the last page is reached
  is where the count is wrong.

**Acceptance criteria:**
- [ ] A report of 200 rows exports 200 data lines
- [ ] Reports of 0, 1, 99, 100, 101 and 201 rows export exactly that many lines
- [ ] No row is written twice
- [ ] A test fails on the old behavior and passes on the new

**Out of scope:**
- Changing the page size
- Other export formats
```

### Good brief (enhancement)

```markdown
> *This was generated by AI during triage.*

## Agent Brief

**Category:** enhancement
**Summary:** Let `report list` show only reports on or after a given date

**Current behavior:**
`report list` prints every report, newest first. There is no way to limit
the list by date, so people filter the output by hand.

**Desired behavior:**
A `--since <date>` option limits the list to reports dated on or after that
day. A date that cannot be parsed prints an error naming the accepted format
and exits with a non-zero code. Without the option, output is unchanged.

**Key interfaces:**
- The `ReportOptions` type gains an optional `since` field (a date).
- The command's option parsing accepts `--since` in `YYYY-MM-DD` form.

**Acceptance criteria:**
- [ ] `report list --since 2025-01-01` prints only reports dated on or after that day
- [ ] A report dated exactly on the given day is included
- [ ] `report list --since not-a-date` exits non-zero and prints the accepted format
- [ ] `report list` with no option prints exactly what it printed before
- [ ] The option is listed in the command's help text

**Out of scope:**
- An end-date option
- Relative dates such as "last week"
```

### Good brief (pull request)

For a pull request, "Current behavior" describes the diff as it stands, and the brief asks the agent to finish or fix it, not to start over.

```markdown
> *This was generated by AI during triage.*

## Agent Brief

**Category:** enhancement
**Summary:** Finish the contributor's `--json` output flag for `report list`

**Current behavior:**
The pull request adds a `--json` flag that writes the report list as JSON.
The success path works and the code follows the command's existing structure.
Two gaps remain: errors still print as plain text under `--json`, and the
flag has no tests.

**Desired behavior:**
With `--json`, all output, errors included, is valid JSON on stdout, and the
exit codes do not change. Without the flag, output is untouched.

**Key interfaces:**
- Under `--json`, the error path emits `{ "error": string }`.
- Reuse the serializer the pull request already adds; do not add a second.

**Acceptance criteria:**
- [ ] `report list --json` prints valid JSON for success and for an error
- [ ] Exit codes match the command without the flag
- [ ] A test covers the success output and one error case
- [ ] Output without `--json` is byte-for-byte the same as before

**Out of scope:**
- Adding `--json` to other commands
- Changing the shape of the success payload the pull request defined
```

### Bad brief

```markdown
## Agent Brief

**Summary:** Fix the export bug

**What to do:**
The export is broken. Look at the main file and fix it.
The function around line 150 has the problem.

**Files to change:**
- src/export/writer.ts (line 150)
- src/types.ts (line 42)
```

What is wrong with it:

- No category and no disclaimer line.
- A vague symptom ("broken") with no input, no observed result.
- File paths and line numbers that go stale.
- No acceptance criteria, so the agent cannot know when it is done.
- No scope boundary.
- No account of current versus desired behavior.
